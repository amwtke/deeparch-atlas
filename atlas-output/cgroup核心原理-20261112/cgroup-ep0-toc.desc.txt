cgroup 核心原理大电影 — 5 条约束 C1~C5：
[C1] 按组限制合计用量 — 管的单位是组不是进程；上限是绝对数，不随开几个进程变；组能套组，父组管整棵子树的合计
[C2] 记实际用量，超限处理看资源类型 — 记物理页、真实 CPU 时间、真实 IO；超了能等的等（CPU、IO），能拒绝的拒绝（进程数），内存只能回收或杀
[C3] 内核负责执行，配额由外部设定 — 归属和上限被管的进程改不了；谁该分多少由管理程序写文件告诉内核
[C4] 在内核已有代码路径上记账，开销要小 — 所有业务共用一个内核；记账只能挂在内核本来就要走的路上，不用的人几乎零成本
[C5] 所有资源共用同一套分组 — 资源种类会不断增加，新增一种不能影响已有的；一笔开销会跨几种资源，所以分组只能有一套

一台 4 核机器上跑着数据库，同事加了一个 8 进程的报表任务，数据库每秒的查询从 690 次掉到 226 次。nice、绑核、ulimit、全机 OOM 都管不住它。往 cgroup 的 cpu.max 里写一行 50000 100000，报表最多只用半颗核；写一行 memory.max 512M，超了只杀报表的进程。这部七集大电影讲清楚：内核是怎么做到的，为什么这样设计，在 Linux 7.0 源码里怎么写的。每一步都在一台 Linux 虚拟机上实测，有终端输出和内核调用栈。

P0 目录：三个问题、七集路线、五条约束、四位设计者。
P1 What：一个组就是一个目录、几个文件；从 docker run 倒推每个数字是谁写进去的；一棵树加一排控制器。
P2 Why：nice、taskset、setsid、ulimit、全机 OOM 各自管不住在哪；你的第一版；v1 的四个问题和 v2 的改法；四种资源放进组里重演，得出五条约束。
P3 How：核心建树、控制器接入；fork、调度结算、缺页、提交 IO、退出五个接入点，每个都有调用栈；CPU 额度用完怎么停，内存超限先回收再杀，进程数拒绝、磁盘排队；五条设计原则。
P4 Origin：2006 年 Paul Menage 把分组抽出来；为什么先有多棵树；Paul Turner 的 CPU 上限；Johannes Weiner 的内存控制器；Tejun Heo 把多棵树收成一棵。
P5 Deep：Linux 7.0 源码三条主线——cpu.max 从写入到限流、内存记账与组内 OOM（以及为什么有时会多杀一个进程）、公共框架的组籍与回调表。
P6 Comparison：对照 Windows Job Object：内存超限一个杀进程、一个拒绝分配；为什么 Windows 不需要公共框架加资源插件。
P7 Synthesis：八个设计想法，再用它们给数据库设计资源组；设计决策总表；这套做法的边界。

人物：Paul Menage、Paul Turner、Johannes Weiner、Tejun Heo。
适合人群：用容器和 Kubernetes、想知道限额在内核里怎么生效的开发者；想把 cgroup、CFS 带宽控制、内存控制器、OOM 连成一条线的内核爱好者；数据库和中间件工程师，想把资源隔离的做法用到自己的系统里。
源码基准：Linux 7.0；实验环境 Ubuntu 26.04，内核 7.0.0-38，4 核虚拟机。
关键词：Linux,cgroup,cgroup v2,容器,Docker,cpu.max,memory.max,OOM,CFS 带宽控制,内存控制器,资源隔离,内核源码

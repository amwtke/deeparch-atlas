- **三份文档各自的戏**:

## 3. 五条约束(用户确认,整体重新编号)

旧的八条压缩重组成五条。**引用格式一律 `C1·按组限制合计用量` 这种「编号·短名」,不许出现裸的 C1、C2。** 旧八条不丢,作为每条根约束下面的「要点」保留在正文里(第二节的约束清单表要有一列写明它由旧的哪几条合成、分别是哪一刀切出来的)。

| 新编号·短名 | 内容 | 由什么合成 | 不可再分性 |
|---|---|---|---|
| `C1·按组限制合计用量` | 管的单位是组不是进程;上限是绝对数,不随对手多少、不随自己开几个进程变;组能套组,父组管整棵子树的合计 | 旧 C1 业务是一组进程 + 旧 C2 上限要是绝对数 + 旧 C7 限额要能层层转包 | 开几个进程是应用的自由;相对权重回答不了「最多多少」;上级管不了下级内部怎么分,但必须管住合计 |
| `C2·记实际用量,超限处理看资源类型` | 账记物理页、真实 CPU 时间、真实 IO;超了以后怎么办由资源的性质决定:会再生的(CPU 时间、IO 带宽)等,能拒绝的(进程数)拒绝,内存既等不来也拒绝不了,只能回收或杀 | 旧 C4 账要记在物理消耗上 + 旧 C5 内存不可压缩 | 预订量(地址空间)不稀缺,物理资源才稀缺;物理页占了不还就没有 |
| `C3·内核负责执行,配额由外部设定` | 归属和上限被管的进程自己改不了,由内核强制;但「谁该分多少」内核不知道也不该知道,由管理程序(systemd、docker 之类)通过文件写进来 | 旧 C3 被管者不可信 + 新:机制与策略分开 | 边界能被进程自己改就不存在边界;哪个业务重要是业务上的事,内核无从判断 |
| `C4·在内核已有代码路径上记账,开销要小` | 所有业务共用一个内核;记账点只能挂在内核本来就要走的路上(调度、缺页、提交 IO、fork),必须便宜;没人设限时这一步几乎不花钱 | 旧 C6 共用一个内核 + 新:怎么融入内核 | 每家一个内核(虚拟机)资源无法互借;记账在最热的路径上,贵了就是给所有人加税 |
| `C5·所有资源共用同一套分组` | 要管的资源种类会不断增加,新增一种不能惊动已有的,所以要「公共骨架 + 插件」;一笔开销又会跨几种资源(写文件先占内存后写盘),所以分组只能有一套 | 旧 C8 一笔开销跨多种资源 + 新:框架要开放 | 资源种类由硬件和业务的发展决定,事先列不完;占内存的人和发 IO 的人不是同一个执行者 |

旧 → 新对照(改写旧稿里的引用时用):

| 旧 | 新 |
|---|---|
| C1·业务是一组进程 | `C1·按组限制合计用量` |
| C2·上限要是绝对数 | `C1·按组限制合计用量` |
| C3·被管者不可信 | `C3·内核负责执行,配额由外部设定` |
| C4·账要记在物理消耗上 | `C2·记实际用量,超限处理看资源类型` |
| C5·内存不可压缩 | `C2·记实际用量,超限处理看资源类型` |
| C6·共用一个内核 | `C4·在内核已有代码路径上记账,开销要小` |
| C7·限额要能层层转包 | `C1·按组限制合计用量` |
| C8·一笔开销跨多种资源 | `C5·所有资源共用同一套分组` |

## 4. 设计哲学:五句话(不单开一章讲,在故事里一句句长出来)

| 哲学 | 一句话 | 根在哪条约束 | 第一节埋在哪 | 第二节在哪被逼出来 | 第三节的实证 |
|---|---|---|---|---|---|
| 核心不认识资源 | 公共的那一层只管「谁和谁一组」,不知道 CPU、内存是什么;每种资源是一个插件 | `C5·所有资源共用同一套分组` | 成品目录里文件名前缀 = 控制器名,`cgroup.` 开头的属于公共层 | 「你的第一版」撞墙那一幕 | `fw.log`(逐个打开控制器)、`table.log`(登记表) |
| 只搭车,不改道 | 不给内核另修一条路;记账点挂在内核本来就要走的路上;没人设限时这一步不走 | `C4·在内核已有代码路径上记账,开销要小` | 「它在系统里的位置」:下面接内核的四条路 | 「骨架放在哪」那一幕(对照虚拟机) | `hooks.log`(调用栈)、`free.log`(没人设限时 0 次) |
| 记账即执法,没有巡查 | 账是消耗的那一刻顺手记的,限是记账的那一刻顺手比的;没有监工 | `C2·记实际用量,超限处理看资源类型` + `C4·在内核已有代码路径上记账,开销要小` | 一句话定义里「按账设限」 | 核心想法那一幕 | `t1`、`t2`、`t3`、`t4` 各段;唯一的定时器只补不查 |
| 内核只给机制,数字由外面写 | 接口是文件;谁该分多少由管理程序决定,内核只负责兑现 | `C3·内核负责执行,配额由外部设定` | 「从一条命令倒推」:五站接力的终点是写文件 | 「谁来定数字」 | 第三节 §2 舞台:`mkdir` 和 `echo` |
| 少留自由 | 凡是插件之间要对账的事,由公共层统一规定;v1 把「树长什么样」留给插件,翻车;v2 收回,只有一棵树 | `C5·所有资源共用同一套分组` | v1 / v2 关键词 | v1 的四个痛与 v2 | 组籍「每个控制器一个格子」、只有一行的 `/proc/<pid>/cgroup` |

每一句第一次出现时,必须是某个具体痛点或某段实测逼出来的结论,不能凭空宣布。第二节的 §12 和第三节的 §15 各有一次「收拢」(把已经在故事里出现过的几句话排在一起),那是收尾,不是首次引入。

## 5. 术语(三份文档统一)

| 术语 | 含义 | 首次引入 |
|---|---|---|
| 组 | 一组进程;外形是 `/sys/fs/cgroup` 下的一个目录 | 第一节 |
| 核心 | cgroup 里和具体资源无关的公共层:树、组籍、文件接口、生命周期通知 | 第一节点到,第二节被逼出来,第三节拆开看 |
| 控制器 | 负责某一种资源的插件(cpu、memory、io、pids……);v1 里叫子系统 | 第一节 |
| 组籍 | 进程身上的一个指针指向的那张卡片(内核里叫 `css_set`),上面每个控制器一个格子,写着「这种资源的账在哪个组上」 | 第二节(概念),第三节(实物) |
| 账 / 账本 | 某个组在某种资源上的那本账,上限(限)就写在账旁边 | 第一节(三个动词),第三节细讲 |
| 零钱 | 每颗核手里预先领好的一小份额度(CPU 一份 5 ms,内存一批 64 页),用来避免每次记账都碰全组共享的数 | 第三节 |
| 接入点 | 内核本来就要走的一条路上,cgroup 搭车的那个位置(fork、调度器结算、缺页、提交 IO、退出) | 第一节点到「四条路」,第三节细讲 |
| 登记表 | 控制器向核心登记的一张固定格式的回调表(建账、入组、fork、退出时核心按表叫人) | 第三节 |
| 搭车 | cgroup 不新建执行路径,只在内核已有的路径上多做一步 | 第二节 |
| 处置 | 超限之后怎么办:等 / 拒绝 / 回收或杀 | 第二节 |

比喻的统一口径:**合租公寓**。几家业务合租一台机器。分户(谁住哪间)只划一次 = 分组是公共的;水表、电表、燃气表 = 不同资源各有各的表(控制器);每户的限额是物业定的,不是表自己定的 = 策略在外;装表不能把全楼的水管重铺一遍 = 只能搭车。第一节已有「合租公寓的分户电表」类比,重构时沿着它展开,不要另起一个比喻体系。

### 6.3 第三节 `stages/03-how/03-how.md`:骨架怎么接进内核

第三节是「Why 之后的阶段」,必须遵守套件的固定骨架:顶部约束清单速查(用 `#### C1 — 短名` 这种四级标题,五条,每条三行:内容 / 不可再分 / 口诀)→ §0 三件事(必须正好三件)→ §1 极简概览图 → 细节 → 约束回扣 → 呼应灵魂问题 → 修订记录。

**§0 的三件事定为:组籍、账本、接入点。**

- 组籍:因为 `C1·按组限制合计用量` + `C3·内核负责执行,配额由外部设定` → 内核要一步从进程找到组,且进程自己改不了 → 进程身上一个指针,指向一张每个控制器一个格子的卡片。属于核心。
- 账本:因为 `C2·记实际用量,超限处理看资源类型` + `C5·所有资源共用同一套分组` → 每个组、每种资源各一本账,限就写在账旁边,挂在同一棵树的节点上。属于控制器。
- 接入点:因为 `C4·在内核已有代码路径上记账,开销要小` → 记账的动作不另起一条路,挂在内核本来就要走的路上;为了便宜,每颗核先留一份零钱。核心和控制器在这里碰头。

# 阶段 1:cgroup 是什么

> 这一节独立成篇:没看过 docker 那一期也能跟上。读完你应该能用一句话说清 cgroup 是什么,能指着 `/sys/fs/cgroup` 下的一个目录说出「这个容器的 CPU 和内存上限写在哪」,并且带着两个问题往下读。
>
> 全篇以 cgroup v2 为准(文件名是 `cpu.max` / `memory.max` 这一套)。还有一套更老的 v1,为什么会有两套,放到下一节讲。

## §0 开场:凌晨两点,报表把数据库挤慢了

先设想一个场景(数字是为了讲清楚而设的,不是实测)。

你手上有一台 4 核 8G 的机器 `host01`,上面跑着一个 mysqld,白天晚上都有查询。同事写了一个每晚跑的报表任务 `report`:为了快,它起 8 个 worker 进程并行做聚合,每个 worker 都把一大块数据读进内存再算。

第一晚上线,两件事同时发生:

- **CPU 被吃光。** 8 个 worker 都是纯计算,4 颗核全满。mysqld 的查询线程要上核得跟 8 个 worker 排队,原来几毫秒的查询变成几十毫秒。
- **内存被吃光。** 8 个 worker 一共吃到 7G 多,机器内存见底。内核被逼到要杀进程腾内存,而全机最胖的进程恰恰是占着 4G 缓冲池的 mysqld。**闯祸的是报表,挨刀的可能是数据库。**

第二天你把启动命令改成这样:

```bash
docker run -d --name job --cpus=0.5 -m 512m report:1.0
```

没用过 docker 也不要紧,这条命令逐段拆开是这样:

| 这一段 | 意思 |
|---|---|
| `docker` | 一个工具:把程序连同它需要的运行环境打成一个包,再把它隔离起来运行。被它跑起来的程序叫「容器」。容器并不是一台小机器,它仍然是宿主机上的普通进程,只是被内核圈了起来 |
| `run` | 子命令:用一个打好的包启动一个容器 |
| `-d` | 放到后台跑(detach)。命令立刻返回,只打印一串容器 ID |
| `--name job` | 给这个容器起名叫 `job`,后面好指代它。不写的话 docker 会随机起一个 |
| `--cpus=0.5` | **这个容器里的所有进程,合计最多用 0.5 颗核的 CPU** |
| `-m 512m` | **这个容器里的所有进程,合计最多用 512 MiB 内存**(`-m` 是 `--memory` 的简写) |
| `report:1.0` | 要跑的那个包,docker 里叫镜像,写法是「名字:版本」。`report` 是本文设想的报表程序,不是一个真实存在的公共镜像 |

这一期只关心加粗的那两段,其余几段和 cgroup 无关。

而且这两段也不是 docker 独有的本事。同一件事不用 docker 也能做,比如交给 Linux 上管服务的 systemd(在 §3.6 的虚拟机里实跑过,这里用 `sleep 30` 代替报表程序):

```bash
$ sudo systemd-run --unit=report-demo -p CPUQuota=50% -p MemoryMax=512M sleep 30
Running as unit: report-demo.service

$ cat /sys/fs/cgroup/system.slice/report-demo.service/cpu.max
50000 100000
$ cat /sys/fs/cgroup/system.slice/report-demo.service/memory.max
536870912
```

![终端留档:systemd-run 限 50% CPU 与 512M 内存,落下的 cpu.max 与 memory.max](pics/01-shot-systemd.svg)

(这类「终端留档图」是把实跑的终端输出原样存成日志再排成图,来历见 §3.3.2 开头的说明。)

写法完全不同(`CPUQuota=50%` 对 `--cpus=0.5`),落下来的却是一模一样的两个数。这两个数是什么、为什么长这样,正是 §3 要倒推的;这里先留个印象:**docker 只是前台,干活的另有其人。**

从此报表再怎么起 worker,合起来也只吃得到半颗核;内存涨到 512M 就到头,真撑爆了死的也只是报表自己,mysqld 毫发无伤。

两个参数,十几个字符,效果立竿见影。但这里有三件事值得停下来想:

1. `--cpus=0.5` 和 `-m 512m` 是 docker 的参数,不是内核的。内核不认识 docker。**这两个数最后是以什么形式交到内核手里的?**
2. report 有 9 个进程(1 主 + 8 worker),限制却是「合起来半颗核、合起来 512M」。**内核怎么知道这 9 个进程算一摊?**
3. mysqld 也在同一台机器、同一个内核上跑,**凭什么报表撑爆了只杀报表?**

这三个问题的答案是同一个东西:cgroup。这一节先回答第 1 个和第 2 个的「表面」(数交到了哪、一摊是怎么圈出来的);内核拿到数之后怎么数、怎么掐,是后面的事。

## §1 一句话定义

**cgroup:内核把一组进程的资源消耗合记成一本账、并按账设限的机制。**

(不到 30 字。)

拆开是三个动词,后面会反复用到:

| 动词 | 意思 | 在开场例子里 |
|---|---|---|
| 分组 | 圈定哪些进程算「一摊」 | report 的 9 个进程是一摊,mysqld 是另一摊 |
| 记账 | 这一摊合起来用了多少,记在同一本账上 | 9 个进程用的 CPU 时间加在一起算,占的内存加在一起算 |
| 设限 | 账上的数到了上限,就不再给 | CPU:每 100 ms 里合计只给 50 ms;内存:合计 512 MiB 封顶 |

名字本身就是这个意思:cgroup = control group,「受控的一组」。

## §2 类比:合租公寓的分户电表

一栋合租公寓,整栋楼只有一路进线(一台机器的 CPU 和内存)。没有分户电表的时候,谁家开十台电暖器,全楼一起跳闸。

物业的办法是给每一户装一块表:

| 公寓 | 机器 | cgroup 里的叫法 |
|---|---|---|
| 整栋楼的总进线 | 整台机器的 CPU / 内存 | 根组 |
| 一户 | 一个容器、一个系统服务 | 一个 cgroup(一个目录) |
| 户里的每个人 | 进程 | 组里的成员 |
| 分户电表 | 这一户合计用了多少 | 记账 |
| 表上设的限额 | 这一户最多用多少 | `cpu.max` / `memory.max` |
| 物业 | 内核 | —— |
| 到限额拉这一户的闸 | 超了只处理这一组 | 限流 / 组内 OOM |

这个类比里能自己推出三条性质,每一条后面都会变成真实机制:

- **表装在入户总管上,不装在每个电器上。** 一户里添了新电器、来了新住客,不用重新登记,电照样走这块表。对应:进程 fork 出来的子进程自动算在同一组里。
- **表只计量、限额,不负责发电。** 电还是电厂发的。对应:CPU 时间还是调度器在分,内存还是内存管理在分,cgroup 只是让它们分的时候多看一眼账。
- **分表可以套总表。** 一层楼一块总表,下面每户一块分表,各户加起来不能超过这层的总表。对应:cgroup 是一棵树,子组受父组限制。

类比到此为止。它说不清的地方(表到底装在内核的哪条路上、闸是怎么拉的)正是后面要钻的。

## §3 从一条命令倒推:两个参数是怎么交到内核手里的

### §3.1 先说结论

- 从你敲回车到内核生效,中间经过 **五站接力**:docker 命令行 → dockerd → containerd(和它的 shim)→ runc → 内核。
- 前四站都是用户态程序,**每一站只做翻译**:把上一站的说法换成下一站听得懂的说法。
- 到内核面前只剩 **三个动作**:建一个目录(建组)、把 pid 写进一个文件(入组)、把数字写进两个文件(设限)。
- 所以内核并不知道什么是容器、什么是 docker。它只看见有人在 `/sys/fs/cgroup` 下面建了目录、写了文件。**cgroup 对外的全部接口就是一棵目录树。**

![一条命令的五站接力:从 docker run 到 /sys/fs/cgroup](pics/01-docker-relay.svg)

### §3.2 五站各自做了什么

先认一下前四站的名字,没用过 docker 的话只要知道它们各是哪一类角色:

- **docker 命令行**:你在终端里敲的那个 `docker` 程序,只负责听懂你的参数再转告出去,自己不跑容器。
- **dockerd**:常驻后台的 docker 主程序(名字末尾的 d 是 daemon,守护进程),真正接单的是它。
- **containerd 和 shim**:dockerd 手下管容器生老病死的管家;shim 是它为每个容器留下的一个小看护进程。
- **runc**:最后真正动手的小工具,负责向内核提要求把容器建出来,建完就退出。

名字不用记,记住分工就行:**前台 → 接单 → 管家 → 动手的人 → 内核。**

| 站 | 是谁 | 收到 | 做了什么 | 交给下一站 |
|---|---|---|---|---|
| ① | docker 命令行 | 你敲的 `--cpus=0.5 -m 512m` | 把人话解析成两个整数 | 一个 HTTP 请求 `POST /containers/create`,里面有 `NanoCpus: 500000000`、`Memory: 536870912`,走本机套接字 `/var/run/docker.sock` |
| ② | dockerd(守护进程) | 上面那个请求 | 把「几颗核」换算成「每个周期多少微秒」,生成一份符合 OCI 标准的 `config.json` | `linux.resources.cpu.quota = 50000`、`cpu.period = 100000`、`memory.limit = 536870912`,外加这个容器的组应该建在哪(`cgroupsPath`) |
| ③ | containerd + shim | 镜像和上面的配置 | 把镜像解成根文件系统,和 `config.json` 摆进同一个目录(叫 bundle),然后叫 runc | 两条命令:`runc create`、`runc start` |
| ④ | runc | bundle 目录 | 读 `config.json`,**建组、入组、写数**;然后让容器进程变身成 report 程序;自己退出 | 对内核的几次建目录、写文件 |
| ⑤ | 内核 | 建目录、写文件 | 记下这个组、组里有谁、上限是多少 | (从这里开始才是 cgroup 真正干活的地方,留给后文) |

OCI 是容器行业约定的一份公共格式。有了它,docker、Kubernetes、podman 可以共用同一个 runc。对这一节来说只要记住:**到 runc 手里的是一份 JSON,里面已经是内核口味的数字了。**

### §3.3 算例:0.5 和 512m 怎么变成那三个数

**CPU 这一边。** 内核不懂「0.5 颗核」。它懂的是另一种说法:**把时间切成一个个周期,每个周期里这一组合计最多用多少 CPU 时间**。周期默认 100 ms。换算一步一步来:

```
--cpus=0.5
  → 命令行换成整数(单位:十亿分之一颗核)    NanoCPUs = 0.5 × 10⁹ = 500 000 000
  → dockerd 取周期 period = 100 ms            = 100 000 μs
  → 配额 quota = NanoCPUs × period ÷ 10⁹      = 500 000 000 × 100 000 ÷ 1 000 000 000
                                              = 50 000 μs
  → runc 写进 cpu.max 的内容                  "50000 100000"
                                               配额   周期   (单位都是微秒)
```

读法:**每 100 000 μs(100 ms)里,这一组合计最多跑 50 000 μs(50 ms)**。50 ÷ 100 = 0.5,对上了。

对账:换算公式就三行,在 dockerd 源码里(moby v27.3.1 `daemon/daemon_unix.go` 153~158 行):

```go
if config.NanoCPUs > 0 {
    period := uint64(100 * time.Millisecond / time.Microsecond)   // 100000
    quota := config.NanoCPUs * int64(period) / 1e9                // 50000
    cpu.Period = &period
    cpu.Quota = &quota
}
```

再多算几个,体会「配额可以比周期大」:

| 你敲的 | `cpu.max` 的内容 | 读法 |
|---|---|---|
| `--cpus=0.5` | `50000 100000` | 每 100 ms 合计 50 ms |
| `--cpus=1.5` | `150000 100000` | 每 100 ms 合计 150 ms |
| `--cpus=2` | `200000 100000` | 每 100 ms 合计 200 ms:机器有多颗核,一组进程在 100 ms 的墙上时间里可以合计跑出 200 ms |
| 什么都不写 | `max 100000` | 不设限 |

注意「合计」两个字。`50000 100000` 不是说「绑在半颗核上」,而是说 9 个进程不管散在哪几颗核上,它们的 CPU 时间加起来,每 100 ms 不超过 50 ms。**谁在做这个加法,是这一期要回答的第一个问题。**

#### §3.3.1 你的视角:0.5 颗核不是把核切开

你读到这里时提出:「0.5 个核,肯定不是把一个 CPU 核分开的计算,而是调度器上时间只能是正常的一半。」

**对,而且这是理解 `cpu.max` 最要紧的一步。** 核切不开:任何一瞬间,一颗核要么整颗在跑你,要么没在跑你,没有「跑半颗」这种状态。所以 0.5 只能是时间上的比例,不是空间上的切分;执行这件事的也确实是调度器。

在你这句话上再拧紧三处:

**① 「一半」是相对谁说的。** 是相对「一颗核跑满」,不是相对「它本来能拿到的」。report 的 8 个 worker 本来能吃满 4 颗核,限成 0.5 之后是原来的八分之一,不是二分之一。更准确的单位是:

```
0.5 颗核 = 50 ms CPU 时间 ÷ 100 ms 墙上时间
```

也就是「每过 1 秒钟,这一组合计只能在核上跑 0.5 秒」。`--cpus=2` 同理:每过 1 秒,合计能跑 2 秒(得有至少两颗核同时在跑它)。

**② 不绑核。** 这 50 ms 不指定在哪颗核上花。可以全在核 0 上,也可以 4 颗核各跑一小段,内核只看加起来的总数。§3.4.1 的实测就是这样:8 个进程散在 4 颗核上,一次各拿 6.0% ~ 6.6%,另一次各拿 4.3% ~ 12.0%,加起来都是半颗核(51.0% / 51.5%)。(要把一组进程钉在某几颗核上是另一个文件 `cpuset.cpus` 的事,这一期不展开。)

**③ 体感不是「慢一半」,而是「跑一阵、停一阵」。** CPU 的主频没有变,在核上的时候是全速;变的是「在不在核上」。

![0.5 颗核的两种时间分布:单线程跑 50 停 50,多核并行时 12.5 ms 烧完后停 87.5 ms](pics/01-half-core-timeline.svg)

| 场景 | 每 100 ms 周期里发生的事 | 观感 |
|---|---|---|
| A:组里 1 个死循环 | 跑 50 ms,然后 50 ms 不许上核 | 走走停停,各占一半 |
| B:组里 8 个 worker,机器 4 颗核 | 4 颗核同时烧同一份配额,4 × 12.5 ms = 50 ms,**12.5 ms 就烧完**;剩下 87.5 ms 整组不许上核 | 猛冲一下,停很久 |

场景 B 是这件事里最反直觉的地方:线程越多、并行度越高,配额烧得越快,停的时间越长。对报表这种后台任务无所谓;但如果被限的是一个在线服务,某个请求恰好落进那 87.5 ms 的停顿里,它的响应时间就凭空多出几十毫秒,尽管整台机器可能很闲。「给容器设了 CPU 上限之后延迟出现毛刺」是线上的常见现象,根子就在这里。

图是按理想情况画的。下一小节用一个完整的例子把两种场景都实跑出来对账。

#### §3.3.2 一个完整的例子:同一份活,放进 0.5 颗核要多久

你接着要求:「举个例子详细说明 cpu=0.5 的具体含义。」下面四个实验都在 §3.6 的虚拟机里实跑(2026-11-13,4 核 8G,内核 7.0.0-38)。

**关于下面的「终端留档图」。** 每个实验配一张图,是把实跑时的终端输出原样存成日志、再排成终端样子的图,不是对着屏幕截的窗口截图。图里每一行都逐字来自日志:命令和输出是真实执行结果,只有提示符 `root@lima-cg:/tmp#` 那几个字是留档脚本打印的。三样东西都在本目录下,可以自己重跑对账:

- 跑实验的脚本:[`src/01-evidence-sessions.sh`](src/01-evidence-sessions.sh)
- 日志原文:`src/logs/*.log`
- 把日志排成图的脚本:[`src/01-render-shots.py`](src/01-render-shots.py)

同一批实验当天先跑过一遍,数字很接近(单任务 4.09 s,四任务 55.45 s);正文一律以留档这一遍为准。

**先说结论。**

- `--cpus=0.5` 的含义只有一句:**每 100 ms 墙上时间里,这一组进程合计只能在核上待 50 ms。**
- 它不减少干活需要的 CPU 时间,只是把这些 CPU 时间在墙上时间里摊开:**墙上时间 ≈ 这一组总共需要的 CPU 时间 ÷ 0.5。**
- 配额用完后进程还活着,只是不在核上;到下一个周期边界才被放回来。
- 它管的是「在核上待多久」,不保证「这段时间能干多少活」(实验 4 会看到这一点)。

**准备:一份正好要 2 秒 CPU 的活。** 一个 Python 循环做 1.1 亿次乘加(`work.py`,源码在下图开头),在这台虚拟机上校准为约 2 秒。程序自己报两个数:墙上时间(从开始到结束,表走了多久)和 CPU 时间(它真正在核上跑了多久)。

**实验 1:一个任务。**

![实验 1 终端留档:同一份活,不设限 2.05 秒,放进 0.5 核的组 4.20 秒](pics/01-shot-half-one.svg)

图里的入组写法 `bash -c 'echo $$ > …/cgroup.procs; exec …'` 和 runc 是同一个顺序:先把自己登记进组,再变身成要跑的程序。

| | 墙上时间 | CPU 时间 |
|---|---|---|
| 不设限 | 2.05 s | 2.05 s |
| 放进 0.5 核的组 | **4.20 s** | 2.14 s |

活没有变多,CPU 时间还是 2 秒出头;表上却走了 4 秒多。多出来的 2 秒去哪了,看组目录里的 `cpu.stat` 这本账(实验前全是 0,所以实验后的读数就是这次实验的量):

| `cpu.stat` 里的字段 | 实验后读数 | 意思 |
|---|---|---|
| `usage_usec` | 2 146 892 | 这一组在核上跑的总时间(微秒) |
| `nr_periods` | 42 | 经过了多少次 100 ms 的周期更替 |
| `nr_throttled` | 42 | 其中多少个周期撞了上限 |
| `throttled_usec` | 2 055 793 | 被挡在核外的总时间(微秒) |

三步对账:

```
① 时间去哪了          在核上 2.14 s + 被挡在核外 2.06 s = 4.20 s = 墙上时间   ✓
② 公式                2.14 s ÷ 0.5 = 4.28 s          ≈ 实测 4.20 s         ✓
③ 每个周期用了多少    2 146 892 ÷ 42 = 51 116 μs      ≈ 配额 50 000(高 2%)
                      任务前后跨了 43 个周期窗口(首尾各沾一点),按 43 算是 49 928 μs
```

第 ③ 步的 2% 出入来自首尾两个不完整的周期;任务跑得越久这个零头越不显眼,实验 3 跑了 556 个周期,就只差千分之一点五。

**实验 2 和实验 3 的前半:亲眼看「跑一阵、停一阵」。** 换一个探针程序(`gaps.py`):死循环里不停读时钟,只要相邻两次读数相差超过 2 ms,就说明「我刚才被拿下核了」,记一笔。每次跑 500 ms,一共三种情况:

| 情况 | 探针看到的 | 对应上图 |
|---|---|---|
| 不设限 | 500 ms 内没有一次超过 2 ms 的停顿 | —— |
| 组里只有探针自己 | 第二段起:跑 50.0 / 50.3 / 49.7 ms,停 49.7 / 45.3 / 55.1 ms | 场景 A:跑 50 停 50 |
| 组里另有 3 个任务在烧 CPU | 第二段起:跑 12.7 / 12.5 / 12.7 / 12.9 ms,停 87.5 / 87.3 / 88.1 / 86.4 ms | 场景 B:跑 12.5 停 87.5 |

两种场景都和理想化的图对上了,场景 B 尤其整齐:4 颗核同时烧同一份配额,4 × 12.5 = 50。

两次的第一段都不规则(一次连着跑了 96.5 ms,一次只跑了 5.0 ms),这是起步效应:探针入组的时刻不在周期边界上。**周期是组自己的节拍,每 100 ms 一格,不会迁就某个进程什么时候开始干活。**

**实验 3 的后半:四个任务并行,做完要多久。** 按公式:4 份 × 2 s = 8 s CPU,÷ 0.5 = 16 s。

![实验 3 终端留档:四个任务并行,不设限 2.64 秒,放进 0.5 核的组 55.58 秒](pics/01-shot-four.svg)

| | 4 个都做完的墙上时间 | 每个任务的 CPU 时间 |
|---|---|---|
| 不设限 | 2.64 s | 2.40 ~ 2.63 s |
| 放进 0.5 核的组 | **55.58 s** | **6.92 ~ 6.97 s** |

不是 16 秒,是 55 秒。先看是不是 cgroup 没守约:

```
usage_usec      27 841 346 μs,周期更替 558 − 2 = 556 次 → 每周期 50 074 μs    配额守住了 ✓
throttled_usec  194.0 s;4 颗核 × 55.58 s = 222.3 s 的「核 × 时间」里,87.3% 处于被挡状态
                                                    (理想值 87.5%)            ✓
```

账是对的。不对的是另一个数:**同样一份活,需要的 CPU 时间从 2.5 秒左右涨到了 6.9 秒。**

**实验 4:追查。** 怀疑和「每次只跑一小会儿」有关,于是只用一个任务(约 0.5 秒 CPU 的活),逐步把配额调小:

![实验 4 终端留档:同一份 0.5 秒 CPU 的活,配额从 50% 调到 5%](pics/01-shot-duty.svg)

| `cpu.max` | 每周期可跑 | 墙上时间 | CPU 时间 | CPU 时间 ÷ 墙上时间 |
|---|---|---|---|---|
| 不设限 | —— | 0.50 s | 0.50 s | —— |
| `50000 100000` | 50% | 1.24 s | 0.63 s | 50.8% |
| `25000 100000` | 25% | 5.27 s | 1.34 s | 25.4% |
| `12500 100000` | 12.5% | 14.46 s | 1.81 s | 12.5% |
| `5000 100000` | 5% | 38.60 s | 1.93 s | 5.0% |

最后一列说明 cgroup 每一次都守住了比例。倒数第二列说明:**每次在核上待得越短,同一份活要花的 CPU 时间越多**,到 5% 时接近原来的 4 倍。

原因我只能给推断,没有证实(待核 #8):这是虚拟机环境的副作用,不是 cgroup 的性质。虚拟机的每颗核在 Mac 这边是一个线程;当它每 100 ms 只忙十几毫秒,Mac 的调度器会把这种「不怎么忙」的线程放到省电的小核或较低的频率上,于是同样的 12.5 ms 里干的活变少了。在真正的物理服务器上不应该有这么大的差距,但方向相同的小幅效应(频率来不及升上去、缓存变冷)是存在的。

这个意外正好说明了一件值得带走的事:**`cpu.max` 记的是时间,不是干了多少活。** 它保证你每周期在核上不超过 50 ms,至于这 50 ms 里核跑得快还是慢,它不管。

**小结:`--cpus=0.5` 到底意味着什么。**

| | 说法 | 证据 |
|---|---|---|
| 保证 | 每个 100 ms 周期,这一组合计在核上不超过 50 ms | 实测每周期 49 983 μs(§3.4.1)、50 074 μs(实验 3) |
| 不绑核、不分人 | 只看合计;组内谁多谁少、在哪颗核上都不管 | §3.4.1:两次实测组内分法不同,合计都是半颗核 |
| 只摊开,不减少 | 需要的 CPU 时间不变,墙上时间 ≈ CPU 时间 ÷ 0.5 | 实验 1:2.14 s CPU → 4.20 s 墙上时间 |
| 用完即停 | 配额烧完到下个周期边界之间,整组不在核上;并行度越高,烧得越快、停得越久 | 探针:跑 50 停 50;跑 12.5 停 87.5 |
| 是上限,不是保底 | 机器忙的时候可能连 0.5 都拿不到;保底是另一个文件 `cpu.weight` 的事 | 这一期后面再讲 |
| 记时间,不记活 | 同样的 50 ms,核慢了干的活就少 | 实验 4 |

到这一步「是什么」就够了。配额用完的那一刻内核具体做了什么、谁在数、下个周期又是谁把它们放出来,是这一期第一个问题的核心,留到后面。

**内存这一边。** 简单得多,只是换单位:

```
-m 512m
  → 512 × 1024 × 1024 = 536 870 912 字节
  → runc 写进 memory.max 的内容  "536870912"
```

| 你敲的 | `memory.max` 的内容 |
|---|---|
| `-m 512m` | `536870912` |
| `-m 4g` | `4294967296` |
| 什么都不写 | `max` |

顺带一个容易漏的:只写 `-m` 不写 `--memory-swap` 时,dockerd 会把「内存 + 交换区」的总量默认设成内存的两倍(同一个文件 317~320 行),也就是 1 GiB。v2 的文件 `memory.swap.max` 只管交换区那一部分,所以 runc 写进去的是 1 GiB − 512 MiB = `536870912`。这个数这一期不展开,知道 runc 一共写了三个文件即可。

### §3.4 落到机器上:runc 的三个动作

runc 拿到 `config.json` 后,按时间顺序做这些事(以 pid 4321 为例):

```
runc create job
  ├─ 生出一个子进程(pid 4321)        此刻它跑的还是 runc 自己的代码,还不是 report
  ├─ ① 建组   在 /sys/fs/cgroup/system.slice/ 下出现目录 docker-9f2c…e1.scope/
  ├─ ② 入组   4321 被登记进这个目录的 cgroup.procs
  └─ ③ 写数   cpu.max ← "50000 100000"    memory.max ← "536870912"    memory.swap.max ← "536870912"

runc start job
  └─ 4321 变身(exec)成 /usr/bin/report    从 report 的第一条指令起,它就已经在组里
       └─ report 起 8 个 worker(pid 4350 ~ 4357)   它们一出生就在组里

runc 退出,容器由 shim 接管
```

三个动作逐个看。

**① 建组 = 建一个目录。** 目录名里那串 `9f2c…e1` 是容器的 64 位 ID。目录建在哪、由谁动手,取决于 docker 用哪种「cgroup 驱动」:

| 驱动 | 谁去建目录 | 目录位置 |
|---|---|---|
| systemd(v2 机器上的默认) | runc 不自己建,而是发消息请 systemd 建一个临时单元,systemd 去建 | `/sys/fs/cgroup/system.slice/docker-<ID>.scope/` |
| cgroupfs | runc 自己 `mkdir` | `/sys/fs/cgroup/docker/<ID>/` |

为什么默认绕 systemd 一道:这台机器上的 cgroup 树本来就是 systemd 在管(每个系统服务都是它建的一个组),两个管理者各建各的容易打架,所以让 runc 去「申请」而不是自己动手。**对内核来说两种驱动没有区别,它看到的都是一次建目录。**

目录一建好,里面立刻就有一堆文件。没有人创建过它们:

```
$ ls /sys/fs/cgroup/system.slice/docker-9f2c…e1.scope/
cgroup.controllers  cgroup.events  cgroup.procs  cgroup.stat  cgroup.subtree_control  …
cpu.max             cpu.weight     cpu.stat      cpu.pressure                         …
memory.max          memory.high    memory.current  memory.events  memory.stat  memory.swap.max  …
io.max              io.stat        io.pressure                                        …
pids.max            pids.current                                                      …
```

上面是节选。在一台真机上数过(内核 7.0,开了 cpuset / cpu / io / memory / pids 五个控制器):新建一个空目录,里面立刻有 62 个文件。

文件名的规律是「谁管的.管什么」:`cpu.` 开头的归 CPU 这一类资源,`memory.` 开头的归内存,`cgroup.` 开头的是组本身的事(成员名单、状态)。刚建好时 `cpu.max` 里是 `max 100000`,`memory.max` 里是 `max`,意思是不设限。

这些文件不在磁盘上。`/sys/fs/cgroup` 是内核提供的一种特殊文件系统(名字叫 cgroup2),**读文件是在问内核一个数,写文件是在改内核里的一个数**。至于内核把数存在哪,留作悬念。

**② 入组 = 把 pid 写进 `cgroup.procs`。** 这里有一个顺序上的讲究,值得单拎出来:

> **先入组,后变身。** 4321 被登记进组的时候,它还没有变成 report。等它 exec 成 report、再 fork 出 8 个 worker,所有这些都发生在「已经在组里」之后。

这就回答了开场的第 2 个问题的表面:内核怎么知道 9 个进程算一摊?**不是事后一个个去认领,而是第一个进程在干活之前就被放进组,之后它生的每一个子进程自动继承这个身份。** 分户电表装在入户总管上,就是这个意思。

#### §3.4.1 你的视角:事后才把主进程写进组,worker 跟不跟?

反问是这样的:不用 docker,直接在宿主机上把 report 跑起来,它已经 fork 完 8 个 worker;这时才手工建一个组,把 **主进程** 的 pid 写进 `cgroup.procs`,再往 `cpu.max` 写 `50000 100000`。8 个 worker 受不受这半颗核的限制?

你的回答:「应该受限。」

**认一半。** 从目的上说你是对的:它们是一家子,本来就该一起受限,这正是 cgroup 想做到的效果,也是大多数人的第一直觉。

**纠一半。** 内核不会替你追认。成员资格只有两条规则:

1. **写 `cgroup.procs` 只搬被写的那一个进程**(连同它自己的全部线程),不搬它已经生出来的子进程。
2. **继承只发生在 fork 的那一刻**:子进程出生时抄一份父进程当时所在的组,此后父子各记各的,父进程再搬家与它无关。

所以结果是:主进程进了新组(它只是在等 worker,本来就不吃 CPU);8 个 worker 还留在原来的组里,照样吃满 4 核。只有主进程 **此后** 再 fork 出来的新 worker,才会生在新组里。

用户口来比更贴切:孩子出生时随父母落户;之后父母迁户口,已经分户单过的孩子不会跟着迁。

**实跑对账。** 2026-11-13 在 §3.6 那台 Lima 虚拟机里实跑(Ubuntu 26.04.1,内核 7.0.0-38,4 核 8G,root 身份)。下面两张是终端留档图(图的来历见 §3.3.2 开头的说明;脚本是 [`src/01-evidence-sessions.sh`](src/01-evidence-sessions.sh) 的 `join` 会话,日志原文在 `src/logs/join.log`)。

先是「只把父进程写进组」:

![终端留档:先起 8 个子进程,后建组只写父进程;子进程留在原组,各吃约 50% CPU,demo 组账上为 0](pics/01-shot-join-1.svg)

逐步读这张图:

1. 父进程是 2993,它已经生出 2995 ~ 3002 八个 `yes`(一个不停输出的死循环,这里只拿它来吃 CPU)。此时父子都在登录会话的组 `session-6.scope` 里。
2. 建组 `demo`,只写 2993,设 `50000 100000`。
3. `demo/cgroup.procs` 里只有 2993;2993 的组变成了 `/demo`,而子进程 2995 的组 **还是原来那个**。
4. 采样 3 秒:8 个 `yes` 各吃 48.8% ~ 53.2%,合计 400%,4 颗核全满;`demo` 的 `usage_usec` 采样前后都是 0。

(每个 50% 左右是 8 个进程抢 4 颗核、各分到半颗,和限额那个 0.5 只是数字碰巧。)规则 1 和规则 2 对上了。

接着做「事后补救」,把 8 个子进程逐个写进 `demo/cgroup.procs`,再采样一次:

![终端留档:把 8 个子进程逐个写进 demo 组后,合计 CPU 降到约 51%,33 个周期全部被限流](pics/01-shot-join-2.svg)

| | 只把父进程写进组 | 9 个进程都写进组 |
|---|---|---|
| 8 个 yes 的 CPU 合计 | 400.0%(各 48.8% ~ 53.2%) | 51.0%(各 6.0% ~ 6.6%) |
| demo 组账上的 CPU 时间 | 0 μs | 采样前后 553 273 → 2 202 717,涨了 1 649 444 μs |
| 经过的周期 | —— | 12 → 45,共 33 个 |
| 平均每个周期 | —— | 1 649 444 ÷ 33 = **49 983 μs** |
| 被限流的周期 | —— | 10 → 43,33 个里 33 个 |

右边这一列值得多看一眼,它是你第一个问题的「现场照片」:

- 平均每周期 49 983 μs,和写进去的 `50000` 只差万分之三。**限额是按周期一格一格兑现的,不是长期平均下来差不多。**
- 这一遍 8 个进程分得很匀(6.0% ~ 6.6%)。但当天第一次跑同一个实验时并不匀:有一个进程拿到 12.0%,其余只有 4.3% ~ 6.6%,合计 51.5%。两次组内的分法不一样,合计都是半颗核。**内核在这一层只管一组的合计,组内谁多谁少不归它管。**
- 33 个周期每一个都撞了限。这些计数来自同一目录下的 `cpu.stat`,后面讲「谁在数、怎么掐」时会回到这个文件。
- 图的最后一步顺手用了 `cgroup.kill`:往这个文件写 1,组里的进程一次全部杀掉。这是「一摊」的另一个用处:想清场时不会有漏网的。

(如果你自己建的组里没有 `cpu.max` 这个文件,说明父目录没把 cpu 控制器往下开,先执行 `echo +cpu > /sys/fs/cgroup/cgroup.subtree_control`。这台虚拟机默认已经开了。)

这条规则带来两个推论,后面都会用到:

- **事后补救追不干净。** 要把 9 个 pid 逐个写进去;而你写的这段时间里它们还可能继续 fork,新生的又落在旧组。所以 runc「先入组、后变身」不是讲究,是必须:在程序的第一条指令之前入组,这一家就不可能有漏网的。
- **反过来,进了组就生不出组。** 普通进程无论 fork 多少层,后代都在同一个组里;想离开得有权限去写别的组的 `cgroup.procs`。「管一摊」的可靠性就建立在这上面。

**③ 写数 = 往两个文件里各写一行。** 没有系统调用专门叫「设置 CPU 限额」,就是普通的 `write`。

把三站的说法并排放,就是完整的对照表:

| 你敲的 | dockerd 翻译成(OCI 字段) | 落到哪个文件 | 写进去的内容 | 意思 |
|---|---|---|---|---|
| `--name job` | 容器 ID `9f2c…e1` + `cgroupsPath` | 目录 `docker-9f2c…e1.scope/` | (建目录) | 建一个组 |
| (容器的第一个进程) | —— | `cgroup.procs` | `4321` | 这个进程入组 |
| `--cpus=0.5` | `cpu.quota=50000` `cpu.period=100000` | `cpu.max` | `50000 100000` | 每 100 ms 合计最多 50 ms CPU |
| `-m 512m` | `memory.limit=536870912` | `memory.max` | `536870912` | 合计最多 512 MiB 内存 |
| (没写 `--memory-swap`) | `memory.swap=1073741824` | `memory.swap.max` | `536870912` | 交换区最多再用 512 MiB |

### §3.5 自己验证

在一台 Linux 宿主机上(systemd 驱动):

```bash
$ ID=$(docker inspect -f '{{.Id}}' job)
$ cd /sys/fs/cgroup/system.slice/docker-$ID.scope

$ cat cpu.max
50000 100000
$ cat memory.max
536870912
$ cat cgroup.procs
4321
4350
…
4357

# 反过来,从任意一个进程查它在哪个组
$ cat /proc/4350/cgroup
0::/system.slice/docker-9f2c…e1.scope
```

最后一条值得记住:**每个进程都能通过 `/proc/<pid>/cgroup` 查到自己属于哪个组**,机器上没有「不属于任何组」的进程,没被特别安排的就在根组或它所在服务的组里。

没有 Linux 机器、只有 Mac 上的 Docker Desktop 时,可以让容器自己读自己的限额(待核 #1):

```bash
$ docker run --rm --cpus=0.5 -m 512m alpine sh -c 'cat /sys/fs/cgroup/cpu.max /sys/fs/cgroup/memory.max'
50000 100000
536870912
```

容器里看到的 `/sys/fs/cgroup` 就是它自己那个组的目录,所以不用拼那串 ID。

### §3.6 手边只有 Mac:要不要一台 Linux

先说结论:**不是必须,但有一台会好很多。**

- **不必须**:这份资料里每条命令都把输出写出来了,只读不跑也能跟上;后面读内核源码更是只需要一份源码。
- **为什么 Mac 本身不行**:cgroup 是 Linux 内核的功能。macOS 的内核是另一套(XNU),没有 `/sys/fs/cgroup`,也没有对应的东西可以凑合。Mac 上的 Docker Desktop 能跑容器,靠的也是在后台悄悄起一台 Linux 虚拟机,容器其实跑在那台虚拟机的内核上。
- **有一台的好处**:§3.4.1 那种「你猜会怎样」的问题,五分钟就能自己验证,不用信我的推断;后面讲 CPU 限流和内存 OOM 时,可以亲眼看到 `cpu.stat` 里的计数在涨、看到组内进程被杀。

所以要动手,就得「虚拟一台」。Apple 芯片的 Mac 上有三条路,由轻到重:

| 方案 | 是什么 | 适合 |
|---|---|---|
| Lima | 开源的命令行工具,一条命令起一台 Ubuntu 虚拟机,有独立的 Linux 内核、systemd、完整的 `/sys/fs/cgroup` | 只想要一个能 `sudo` 的 Linux 终端做实验(推荐) |
| OrbStack | 带界面的轻量替代品,同时给 docker 和 Linux 机器,启动最快 | 还想顺手在 Mac 上直接用 `docker` 命令 |
| UTM / Parallels | 完整的图形化虚拟机 | 想要一台带桌面的 Linux,做 cgroup 实验用不上 |

**Lima 是什么。** 名字是 Linux Machines 的缩写,一个开源的命令行小工具,作用只有一个:在 Mac 上起一台 Linux 虚拟机,并且把麻烦事替你做掉。它自己不是虚拟机,底下用的是 macOS 自带的虚拟化能力(或 QEMU);它负责的是下载系统镜像、建虚拟机、开机、配好登录,让你敲一条命令就得到一个 Linux 终端。可以把它理解成「命令行版的、只管 Linux 的 VirtualBox」。

三点帮助判断要不要装:

- **它和 docker 的关系**:Docker Desktop、Colima、Rancher Desktop 这些让 Mac 能跑容器的工具,背后都要起一台 Linux 虚拟机;Colima 和 Rancher Desktop 用的就是 Lima。区别只是它们把虚拟机藏起来只露出 `docker` 命令,而直接用 Lima 是把这台虚拟机本身交给你 —— 做 cgroup 实验要的正是后者,因为要进去看 `/sys/fs/cgroup`。
- **它里面是真的 Linux**:有自己的内核、自己的 systemd,不是模拟层。在里面建 cgroup、写 `cpu.max`、把进程撑到 OOM,碰到的都是真内核的行为,而且只影响虚拟机,不影响 Mac。
- **它对 Mac 做了什么**:brew 装几个程序;虚拟机的磁盘放在 `~/.lima/` 下;默认会把你的 home 目录以只读方式挂进虚拟机方便取文件。不用了 `limactl delete cg` 加 `brew uninstall lima` 就干净了。

**它用的是芯片原生的虚拟化吗?** 是。和 Intel 那边是同一个思路,只是每一层换了名字:

| 层 | Intel + Linux 上 | Apple 芯片 + macOS 上 |
|---|---|---|
| CPU 硬件能力 | VT-x(客户机模式 + EPT 二级页表) | ARM 虚拟化扩展(EL2 特权级 + 第二阶段页表) |
| 内核暴露的接口 | KVM | Hypervisor.framework |
| 搭出一台虚拟机的程序 | QEMU 等 | Virtualization.framework(Lima 2.3.0 默认用它,实测见下) |
| 你敲的工具 | virsh / vagrant | Lima |

Mac 是 arm64 芯片,虚拟机里跑的也是 arm64 的 Linux,所以客户机的指令直接在真 CPU 上执行,不做翻译,速度接近原生;只有碰到特权操作才陷出来交给宿主处理。

顺带和 §5 对上:这正是「虚拟机」和 cgroup 的分界。虚拟机靠 CPU 硬件切出一台假机器,里面有一个完整的 Linux 内核;在 macOS 看来,整台虚拟机只是一个普通进程。而 cgroup 的账,是虚拟机里那个 Linux 内核自己在记。

2026-11-13 在这台 Mac 上实际装了一遍(Lima 2.3.0),能用的命令是这几条:

```bash
$ brew install lima
$ limactl start --name=cg --cpus=4 --memory=8 --containerd=none --tty=false template:ubuntu-lts
                                    # 起一台 4 核 8G 的 Ubuntu,对上本文的例子
$ limactl shell cg                  # 进去,之后就是 Linux 终端(里面的用户名是 lima,sudo 免密)
$ stat -fc %T /sys/fs/cgroup        # 输出 cgroup2fs,说明是 v2
$ limactl stop cg                   # 不用时关机;limactl start cg 再开,十秒左右
```

**自己进这台 Linux 的终端。** 在 Mac 上另开一个终端窗口,敲 `limactl shell cg` 就进去了,提示符变成 Linux 的;`exit` 或 Ctrl-D 退出,退出后虚拟机还在后台跑。几个实测过的细节:

- 进去后的当前目录和你在 Mac 上敲命令时的目录相同。Mac 的 home 目录被只读挂进了虚拟机,所以在仓库目录下进去,能直接看到这份资料和脚本,但不能在里面写文件(要写就去 `/tmp` 或 `~`)。
- 里面的用户叫 `lima`,`sudo` 不要密码;cgroup 实验基本都要 root,`sudo -i` 切成 root 最省事。
- 重跑本文的实验:在仓库目录下进虚拟机,执行 `sudo bash atlas-output/cgroup核心原理-20261112/stages/01-what/src/01-evidence-sessions.sh join`。最后一个词换成 `env` / `systemd` / `half1` / `probe` / `four` / `duty` 就是其余几个实验。

`--containerd=none` 是踩坑后加的:不加的话 Lima 会顺手从 GitHub 下一个两百多兆的容器工具包,这边网络下它每分钟不到 3 MB,首次启动卡了十几分钟;做 cgroup 实验用不上它,关掉后开机只要 11 秒。(说明:我实际走的是先建虚拟机、再用 `limactl edit cg --set '.containerd.user = false | .containerd.system = false'` 关掉它;上面一步到位的 `--containerd=none` 是照 `limactl start --help` 列出的参数写的,这个写法本身没单独跑过。)

## §4 一张全景图:cgroup 的外形

把 §3 落下的东西摆到一张图上。还是那台 4 核 8G 的 `host01`,报表容器 job 和数据库容器 db 都在:

![cgroup 的外形:一棵目录树,每个目录是一个组](pics/01-overview.svg)

从图上能读出来的五件事:

1. **cgroup 的外形是一棵目录树。** 根是 `/sys/fs/cgroup/`,代表整台机器;往下每个目录是一个组。
2. **容器不特殊。** `sshd.service` 这样的普通系统服务也是一个组,只是没人给它写限额(`max`)。容器只是「被写了数的组」。
3. **一个组的全部配置就是目录里几个文件的内容。** job 和 db 的区别,从 cgroup 的角度看只是 `cpu.max`、`memory.max` 里的数不同、`cgroup.procs` 里的 pid 不同。
4. **每个进程恰好在一个组里。** 4321 在 job 的组里,2210 在 db 的组里,不会同时出现在两处。
5. **图的右下角是空的。** 文件背后内核做了什么,图上只有四个问号。它们就是这一期剩下的全部内容。

### §4.1 它管的不止 CPU 和内存:一棵树 + 一排控制器

**结论:cgroup 不是「限 CPU 和内存的工具」。它是一个框架:一棵组的树是公共的,具体管哪种资源,由一个个叫「控制器」的插件负责。CPU 和内存只是其中两个。**

(这一小节是读完前三节后补的。开场的例子只用了 `--cpus` 和 `-m` 两个参数,容易让人以为 cgroup 就管这两样。)

在真机上问一句「这个内核认识哪些控制器」:

```
# cat /sys/fs/cgroup/cgroup.controllers
cpuset cpu io memory hugetlb pids rdma misc dmem
```

9 个。一个组的目录里,文件名的前缀就是控制器的名字:`cpu.max` 归 cpu 控制器,`memory.max` 归 memory 控制器,`io.max` 归 io 控制器,`pids.max` 归 pids 控制器。以 `cgroup.` 开头的那些(比如 `cgroup.procs`)不属于任何一种资源,属于公共的那一层。

最常用的四个:

| 控制器 | 管什么 | 上限写在哪 | 超了会怎样 |
|---|---|---|---|
| cpu | CPU 时间 | `cpu.max` | 这组进程停到下一个周期 |
| memory | 物理内存(包括读写文件时的缓存) | `memory.max` | 先回收,回收不动就在组里杀进程 |
| io | 每块磁盘的读写速度 | `io.max` | 读写请求排队等 |
| pids | 进程和线程的个数 | `pids.max` | 再 fork 就失败 |

§1 的三个动词(分组、记账、设限)对这四行都成立:分组只有一套,四种资源共用;记账和设限每种资源各做各的。

这一期深挖的是 cpu 和 memory 两个,因为它们对应开头的两个问题。另外两个在第二节 §10.8 实跑;「公共的一层和控制器怎么配合」在第三节 §9 讲。把管资源这件事拆成「公共骨架 + 插件」的做法,本身是一个可以带到别的系统里去的设计,第三节 §9.7 专门说。

## §5 cgroup 不是什么

四个容易和它混在一起的东西。前三个是它的邻居,解决的是不同的问题或者同一个问题的弱化版:

| 容易混的 | 它管的是 | 作用的单位 | 和 cgroup 差在哪(用 job 的例子) |
|---|---|---|---|
| **namespace** | 进程**看得见什么**(进程号、网络、挂载点的视图) | 一组进程的视图 | 它不记账也不设限。容器 job 里敲 `free -m`,看到的还是宿主机的 8G:namespace 没把内存这个「视图」隔开,而限额在 cgroup 那边,是另一套东西。一句话:namespace 管看得见什么,cgroup 管用得了多少 |
| **ulimit**(`setrlimit`) | 单个进程的上限 | **每个进程各算各的** | 给 report 设「每进程最多 512M」,9 个进程就是各有 512M、合计 4.5G,照样把机器撑爆。而且它限内存限的是虚拟地址空间(`RLIMIT_AS`),不是真正占住的物理内存;限 CPU 限的是累计秒数(`RLIMIT_CPU`,到点发信号杀进程),表达不了「每 100 ms 最多 50 ms」这种速率 |
| **nice** | 抢 CPU 时的相对优先权 | 单个线程 | 它只在有人争的时候起作用:把 8 个 worker 都调到 nice 19,mysqld 忙的时候它们会让,但没有「上限」这个概念,机器空闲时照样吃满 4 核;而且多开一个 worker 就多一份权重。它管不了内存 |
| **虚拟机** | 切一份虚拟硬件给你 | 一台假机器 | cgroup 不切硬件、不预留。512 MiB 不是先划出来搁着,而是 job 用到 512 MiB 的那一刻被拦住;job 没用满的部分,别人可以用 |

还有一个反过来的误会:**cgroup 不等于容器。** 容器是 namespace + cgroup + 根文件系统三样拼起来的;cgroup 单独就能用,systemd 管的每个服务都在自己的 cgroup 里,和容器无关。

ulimit 和 nice 这两行其实已经在回答「为什么需要 cgroup」了:它们都以单个进程为单位,而你要管的是「一摊」。下一节从这里接着往下挖。

## §6 关键词速查表

| 术语 | 一句话说明 |
|---|---|
| cgroup(控制组) | 一组进程 + 这组进程合用的一本资源账;外形是 `/sys/fs/cgroup` 下的一个目录 |
| cgroup 文件系统(cgroup2) | 内核提供的特殊文件系统,挂在 `/sys/fs/cgroup`;建目录 = 建组,读写文件 = 读写内核里的数 |
| 控制器(controller) | 负责某一类资源的那部分内核代码:`cpu`、`memory`、`io`、`pids` 等;文件名的前缀就是控制器的名字 |
| 层级(hierarchy) | 组与组的父子关系,也就是目录树;子组受父组的限额约束 |
| `cgroup.procs` | 一个组的成员名单;把 pid 写进去 = 让这个进程入组 |
| `cpu.max` | CPU 上限,内容是 `配额 周期`(微秒),如 `50000 100000` = 每 100 ms 合计最多 50 ms |
| `memory.max` | 内存上限,单位字节,如 `536870912` = 512 MiB;超了先回收,回收不动就在组内杀进程(OOM) |
| v1 / v2 | cgroup 的两套接口。v1 每类资源各一棵树(文件名如 `cpu.cfs_quota_us`),v2 只有一棵树(`cpu.max`)。本期全程用 v2 |
| cgroup 驱动 | 容器运行时用哪种方式建组:`systemd`(请 systemd 建)或 `cgroupfs`(自己建目录) |

## §7 它在系统里的位置

```
 上面(使用者)    docker / containerd / runc        kubelet          systemd
                       └───────── 都只是在建目录、写文件 ──────────┘
 接口                 /sys/fs/cgroup(cgroup 文件系统)
 ════════════════════════════════════════════════════════════════ 用户态 / 内核
 cgroup 本体          一棵组的树:哪些进程算一摊
 下面(被它管的)    调度器(CPU 时间)   内存管理(物理内存)   块层(磁盘 IO)   fork(进程数)
 平行(邻居)        namespace          ulimit              nice / 优先级
```

三句话读这张图:

- **上面**:你平时接触的 docker、Kubernetes、systemd,在资源限制这件事上都是 cgroup 的「前台」。它们各有各的参数写法(`--cpus`、`resources.limits.cpu`、`CPUQuota=`),落到内核都是同一批文件。
- **下面**:cgroup 自己不发 CPU 时间,也不发内存。发 CPU 的还是调度器,发内存的还是内存管理。cgroup 做的事,是让这些子系统在干活的时候认得「组」:这一笔算在哪个组头上、这个组到没到上限。
- **平行**:namespace、ulimit、nice 是邻居,区别见 §5。

## §8 留下的悬念

这一节只讲到「数字交到了内核手里」。接下来的问题一个比一个硬:

1. **在这之前呢?** cgroup 2007 年才进内核。之前的十几年里,一台机器上跑多个互不相让的服务,大家是怎么办的?ulimit 和 nice 明明早就有,它们到底差在哪一口气?
2. **那些文件不在磁盘上,数存在哪?** 写进 `cpu.max` 的 `50000 100000`,内核把它记在了什么东西上?
3. **谁在数那 50 ms?** 9 个进程散在 4 颗核上各跑各的,「合计」是谁在加?每跑一微秒就加一次吗?那得多慢?
4. **数满了怎么掐?** 一个周期里 50 ms 用完了,剩下的 50 ms 这 9 个进程处在什么状态?是被杀了、睡了、还是别的?下个周期又是谁把它们放出来?
5. **内存的账比 CPU 难在哪?** CPU 时间用完了,下个周期又有;内存占了不还。512 MiB 满了以后内核先做什么、最后才做什么?真到杀进程那一步,为什么只在组里挑、怎么挑?
6. **为什么有 v1 和 v2 两套?** 同一个内核功能做了两遍,第一遍错在哪?

第 1 个和第 6 个是下一节的事;第 2~5 个要到讲架构和源码时才能答完。

## §9 呼应灵魂问题

你带来的两个问题,这一节各走了一小步:

| 你的问题 | 这一节拿到的 | 还缺的 |
|---|---|---|
| 往 `cpu.max` 写 `50000 100000`,内核怎么让这组进程最多吃半颗核? | 这行字的来历(`--cpus=0.5` 的换算)、它的读法(每 100 ms 合计 50 ms)、它写在哪、「这组进程」是怎么圈出来的(先入组后变身,子进程继承) | 内核收到之后的一切:账记在哪、谁在数、数满了怎么掐(悬念 2 / 3 / 4) |
| 容器 OOM 只杀容器里的进程,边界谁划的、账怎么记? | 边界就是组:一个目录 + 一份成员名单;上限是 `memory.max` 里的一个数;每个进程恰好属于一个组 | 一页内存记到组头上的那一刻发生了什么、满了以后先回收还是先杀、为什么只在组内挑(悬念 5) |

粗略估计:两个问题都只闭环了一成多 —— 我们知道了「问题里的每个词指的是什么」,还不知道任何一步「怎么做到」。这正是这一节的本分。

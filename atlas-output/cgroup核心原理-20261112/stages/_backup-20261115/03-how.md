# 阶段 3:cgroup 大致怎么工作

上一节的结论是一句话:用「每个进程多带一个组籍 + 每次消耗资源时多记一笔」,换「对任意一组进程的合计设限」。这一节把这句话拆开看:组籍带在哪、那一笔记在哪、超了之后是谁动的手。

讲法是跟着一个进程走。主角是 report 的一个 worker,从它被 fork 出来开始,到它跑 CPU、要内存、被限流、最后被杀,一共五个时刻(t0 ~ t4)。每个时刻讲两件事:**发生了什么**(谁、在哪一刻、改了哪本账),以及**为什么这么记才扛得住**(这笔账每秒要记几十万次)。每个时刻都在实验机上抓了现行。

只讲 cgroup v2,不贴内核源码。跟踪输出里会露出几个内核函数名,只当路牌用,不展开。

## 约束清单速查(C1 ~ C8)

#### C1 — 业务是一组进程
管的单位必须是「组」,管的是合计。
**不可再分**:开几个进程是应用的自由,内核无法预知,也不能禁止。
**口诀**:账户不能挂在进程上。

#### C2 — 上限要是绝对数
上限不随对手多少、不随自己进程数变化。
**不可再分**:相对权重只能回答「谁多」,回答不了「最多多少」。
**口诀**:要能对别人做承诺。

#### C3 — 被管者不可信
组籍和上限由内核强制、管理员掌握。
**不可再分**:只要边界能被进程自己改,就不存在边界。
**口诀**:栅栏不能让里面的人自己围。

#### C4 — 账要记在物理消耗上
记物理页、真实 CPU 时间、真实 IO。
**不可再分**:地址空间这类「预订量」不稀缺;页缓存这类消耗不挂在任何进程名下。
**口诀**:记花掉的,不记订下的。

#### C5 — 内存不可压缩
超了只能回收或杀,所以杀的范围必须有边界。
**不可再分**:CPU 时间每个周期都有新的,物理页占了不还就没有。
**口诀**:CPU 可以等,内存等不来。

#### C6 — 共用一个内核
隔离不能靠每人一套内核;记账在最热的路径上,必须便宜。
**不可再分**:预留出去的资源无法互借;要互借就必须同处一个内核。
**口诀**:记账不能比干活还贵。

#### C7 — 限额要能层层转包
组套组,父组的上限约束整棵子树。
**不可再分**:上级管不了下级内部怎么分,但必须管住合计。
**口诀**:是树,不是一排。

#### C8 — 一笔开销跨多种资源
所有资源必须共用同一套分组。
**不可再分**:占内存的人和发 IO 的人不是同一个执行者,两边必须能互相查到对方的组。
**口诀**:只能有一棵树。

## §0 从「为什么」走到「怎么做」:三件事记住

上一节 §8.1 的核心想法里有三个名词:组籍、组的账、组的限。这一节的全部内容,就是把这三样东西落到内核里。worker 一生中碰到的,也只有这三样。

### §0.1 组籍:进程身上的一个指针

因为 `C1·业务是一组进程`(管的是组)和 `C3·被管者不可信`(归属不能由进程自己说了算)→ 要解决「内核在任何时刻都能从一个进程立刻找到它的组,而且这个归属进程自己改不了」→ 所以每个进程在内核里的档案上多一个指针,指向一张**组籍**(内核里叫 `css_set`)。组籍上写着「这个进程在 CPU 上归哪本账、在内存上归哪本账」。同一个组的进程指向同一张组籍;fork 的时候,子进程抄走的就是这个指针。

### §0.2 组的账:挂在树节点上,每种资源一本

因为 `C4·账要记在物理消耗上`(记的是花掉的)和 `C6·共用一个内核`(记账在热路径上)→ 要解决「消耗发生的那一刻就记到组头上,而且记这一笔要足够便宜」→ 所以每个组、每种资源各有**一本账**,挂在组的树节点上;记账的动作直接埋在消耗资源的那条路上(调度器结算运行时间的地方、内核分配物理页的地方);为了便宜,每颗核先在自己手里留一份**零钱**,零钱花完才去动全组共享的那本账。

### §0.3 组的限:写在账旁边,记账时顺手比

因为 `C2·上限要是绝对数` 和 `C5·内存不可压缩`(超了必须当场处置)→ 要解决「不靠任何人巡查,超限的那一刻就被发现并处置」→ 所以**限额就写在账的旁边,每次记账都是「加上去,看超没超」**。CPU 超了,这个组停到下个周期;内存超了,先在组内回收,收不动就在组内杀。

### §0 结论

| 三件事 | 是什么 | 为什么存在 |
|---|---|---|
| 组籍 | 进程身上的一个指针,指向一张写着「各种资源的账在哪」的卡片 | 让内核一步就能从进程找到组;进程自己改不了(`C1·业务是一组进程`、`C3·被管者不可信`) |
| 组的账 | 每个组每种资源一本,挂在树上;每颗核另有一份零钱 | 消耗发生时当场记到组头上,并且便宜(`C4·账要记在物理消耗上`、`C6·共用一个内核`、`C7·限额要能层层转包`) |
| 组的限 | 写在账旁边的一个数;记账时顺手比较,超了当场处置 | 不需要巡查就能兑现绝对上限(`C2·上限要是绝对数`、`C5·内存不可压缩`) |

三者的关系:**进程 →(组籍)→ 账 →(账旁边)→ 限**。worker 每消耗一点资源,内核就顺着这条链走一遍。

还有一层意思先放在这里,§9 展开:这三件事并不专属于 CPU 和内存。**组籍是公共的,一张管所有资源;账和限是每种资源各有一套。** 这条分界线,就是 cgroup 作为一个「框架」的分界线:公共的部分只做一遍,磁盘 IO、进程数这些资源各自只要补上自己的账和限。下面跟着 worker 走的时候只看 CPU 和内存两条线,因为它们对应你的两个灵魂问题;走完之后再把视角拉开。

## §2 开场之前:舞台是怎么搭起来的

**结论:`mkdir` 和 `echo` 做的事,就是在内核里建账和往账上写数。/sys/fs/cgroup 下面的每个文件,都是某本账的一个窗口。**

worker 出生之前,管理员已经做了三件事。每一件在内核里对应什么:

| 管理员做的 | 内核里发生的 | 对应哪件事 |
|---|---|---|
| `mkdir /sys/fs/cgroup/host01/report` | 树上多一个节点 report;父组允许它管哪几种资源,就给它建哪几本账(这里是 CPU、内存、进程数) | 组的账 |
| `echo '50000 100000' > report/cpu.max` | 把这两个数写进 report 的 CPU 那本账:每 100 000 μs 一个周期,每周期额度 50 000 μs | 组的限 |
| `echo 300M > report/memory.max` | 把 76 800 页(300 MiB ÷ 4 KiB)写进 report 的内存那本账,作为上限 | 组的限 |

这三步都只动了账,没有碰任何进程。此刻 report 组里一个进程都没有。

这些文件的主人是 root,普通进程打不开(上一节 §10.3 试过,`Permission denied`)。这就是 `C3·被管者不可信` 的落点:账和限放在被管的进程够不着的地方。

实验环境说明。这一节的实验都在专用实验机 cg-lab 上跑(Ubuntu 26.04.1,内核 7.0.0-38,4 核 4G)。抓现行用的是内核跟踪工具 bpftrace:写几行脚本,告诉它「内核执行到某个函数时,把这几个数打印出来」。下面会出现的路牌:

| 路牌(内核函数 / 结构) | 它是什么 |
|---|---|
| `css_set` | 组籍 |
| `cgroup_post_fork` | fork 快结束时,把新进程挂到组籍上的那一步 |
| `__account_cfs_rq_runtime` | 某个组在某颗核上刚跑掉一段时间,记一笔 |
| `sched_cfs_period_timer` | 每个周期响一次、给组补额度的定时器 |
| `throttle_cfs_rq` / `unthrottle_cfs_rq` | 在某颗核上给这个组挂上 / 摘下「限流中」的牌子 |
| `throttle_cfs_rq_work` | 某个进程看到牌子后下场 |
| `try_charge_memcg` / `page_counter_try_charge` | 给组记若干页的账 / 真正去改组的计数器 |
| `try_to_free_mem_cgroup_pages` | 在某个组的范围内回收内存 |
| `mem_cgroup_out_of_memory` / `oom_badness` | 组内 OOM / 给一个进程打分 |

## §3 t0 出生:fork 的那一刻,组籍是怎么带上的

**结论:子进程不需要「加入」组。fork 把父进程的组籍指针抄给它,它一出生就在组里。整个过程不新建任何东西,只是一张已有的组籍上多挂了一个进程。**

### §3.1 概念:进程、组籍、账

每个进程在内核里有一份档案。档案里有一个指针,指向一张组籍。组籍上的内容很少,主要是一排指针:CPU 的账在哪、内存的账在哪、进程数的账在哪……每种资源一个。

入组分两种情况:

- **写 `cgroup.procs`**(把一个已有的进程搬进组):内核给它换一张组籍。只换它自己的,它已经生出来的子进程不动(第一节 §3.4.1 实测过)。
- **fork**:子进程直接用父进程那一张。

所以开场那个两行的小脚本 `ingroup` 才要「先入组、后变身」:先把自己写进 `cgroup.procs`,换上 report 的组籍,再变身成要跑的程序。此后它 fork 出来的每一个 worker 都带着同一张组籍。

### §3.2 实跑:抓 fork 的那一刻

跟踪脚本(`src/prog/t0-fork.bt`)只有两个探针:一个在「进程被搬进组」时打印,一个在 `cgroup_post_fork` 结束时打印父子两个进程的组籍地址。

```
# bpftrace t0-fork.bt > t0.out 2>&1 &
# ./ingroup report python3 report.py 3 0.2 &
# grep -v -e Attached -e '^$' t0.out

fork  父 7405(report)的组籍 0xffff0000c40f8400   子 7407 的组籍 0xffff0000c40f8400   这张组籍上现在有 2 个进程
      这张组籍里写着:CPU 的账 → 0xffff0000c0dae100(组 report)   内存的账 → 0xffff0000c5794a40(组 report)
fork  父 7405(report)的组籍 0xffff0000c40f8400   子 7408 的组籍 0xffff0000c40f8400   这张组籍上现在有 3 个进程
fork  父 7405(report)的组籍 0xffff0000c40f8400   子 7409 的组籍 0xffff0000c40f8400   这张组籍上现在有 4 个进程

# for p in $(pgrep -x 'report|report-w'); do echo "$p $(cat /proc/$p/cgroup)"; done

7407 0::/host01/report
7408 0::/host01/report

```

![终端留档:入组一次,fork 三次,父子进程的组籍是同一个地址,组籍上的进程数从 2 涨到 4](pics/03-shot-t0.svg)

**读数。**

- 第一行:pid 7405 入组时名字还叫 `ingroup`,入组之后才 exec 成 python,再改名叫 report。先入组,后变身。
- 三次 fork,父子的组籍是同一个地址 `0x…c40f8400`。子进程没有得到一张新的组籍,只是多了一个指向旧组籍的指针。
- 组籍上的进程数 2 → 3 → 4:内核在这张组籍上记着「有哪些进程指着我」。上一节 §10.3 的 `cgroup.kill` 能一个不漏,靠的就是这份名单。
- 第三行是组籍的内容:CPU 的账和内存的账是两个不同的地址,但都属于组 report。
- `/proc/<pid>/cgroup` 里那一行 `0::/host01/report`,是内核顺着「进程 → 组籍 → 组」现查出来的,不是存在进程身上的一个字符串。

### §3.3 再逼问:为什么中间要隔一张组籍

为什么不让进程直接指向组?

- **因为一个进程要找的不是「组」,是「账」。** 调度器只关心 CPU 的账在哪,内存分配只关心内存的账在哪。组籍把这几个答案提前摆好,记账时一步就能拿到,不用先找组、再在组里找账。记账每秒发生几十万次,这一步省得值(`C6·共用一个内核`)。
- **因为同组的进程答案完全一样。** 400 个 worker 共用一张组籍,fork 时什么都不用新建(`C1·业务是一组进程`)。
- **因为归属要内核说了算。** 进程能改的只有自己内存里的东西;这个指针在内核的档案上,只有写 `cgroup.procs`(受文件权限管)和 fork(只能继承)两条路能改它(`C3·被管者不可信`)。

| 没有它会坏在哪 | 它解决了 |
|---|---|
| 每次记账都要从进程出发重新查「它属于哪个组、那个组的账在哪」 | 一步拿到账 |
| fork 时要为子进程登记归属,多一次分配 | fork 只多一个指针 |
| 归属如果存在进程能改的地方,就等于没有边界 | 指针在内核档案上,进程碰不到 |

悬念:worker 生出来了,开始烧 CPU。它每跑 1 毫秒,report 组的账上怎么就多了 1 毫秒?

## §4 t1 跑起来:CPU 的账是怎么记的

**结论:调度器每次结算「当前进程刚才跑了多久」时,顺手从这个组在这颗核上的零钱里扣掉同样多。零钱扣完了,才去组的公共额度池里领下一份,一份 5 ms。实测 2 秒里记了 1660 笔账,只有 181 笔碰了公共池。**

### §4.1 概念:一个池子,四份零钱

report 的 CPU 账由两层组成(图在 §6):

- **公共额度池**:全组只有一个。周期定时器每 100 ms 把它补到 50 ms(就是 `cpu.max` 里的两个数)。它被 4 颗核共用,改它要加锁。
- **每颗核一份零钱**:report 组在核 0、核 1、核 2、核 3 上各有一份。worker 在哪颗核上跑,就花哪颗核上的零钱。零钱只有本核会碰,不用锁。

记账的时机不用专门安排。调度器本来就要不停地结算「当前进程跑了多久」:时钟中断来的时候(这台机器每 1 ms 一次)、进程被换下去的时候。cgroup 只是在这个结算动作后面加了一步:**这段时间也从它所在组的本核零钱里扣掉。** 找「它所在组」用的就是 §3 的组籍。

零钱扣到零以下,就去公共池领一份。领的时候要加锁,但这种事不常发生。

### §4.2 实跑:数一数记了多少笔

report 组限半颗核,8 个 worker。跟踪脚本(`src/prog/t1-cpuacct.bt`)统计 2 秒。

![终端留档:2 秒内记账 1660 次、合计 1000 ms,其中 181 次去公共池领额度,绝大多数一次领 5 到 6 毫秒](pics/03-shot-t1.svg)

**算例。**

- 2 秒 × 半颗核 = 1000 ms。跟踪脚本把每一笔账的金额加起来,正好 1000 ms。组的 CPU 用量不是事后统计出来的,就是这一笔笔账的和。
- 周期定时器 2 秒响 20 次,每 100 ms 一次。
- 181 次领额度 ÷ 20 个周期 ≈ 每周期 9 次。每周期 50 ms、一份 5 ms,最多领 10 份,量级对得上。
- 181 次里有 157 次领到的是 5 ~ 6 ms。比 5 ms 多出来的零头,是补上一次透支的部分:零钱可能被扣成负数(时钟中断 1 ms 才来一次,来的时候才发现花超了),下次领的时候先把欠的补上。不足 5 ms 的那十几次,是池子里剩的不够一整份了,剩多少领多少。
- **1660 笔账里,只有 181 笔(11%)碰了全组共享的池子,其余 89% 只改了本核自己的零钱。**

留档图里 `cpu.stat` 的 `usage_usec` 前后差 1 450 575 μs,比 1000 ms 多。这不矛盾:这两次读数夹着整条 bpftrace 命令,包括它启动和挂探针的那段时间(将近 1 秒),而脚本只统计挂好之后的 2 秒。

### §4.3 再逼问:为什么要有零钱

**如果没有零钱,每一笔都直接从公共池里扣?**

4 颗核每毫秒都要去改同一个数,每次都要抢同一把锁。组里进程越多、核越多,抢得越凶。记账的开销会和干活的开销抢 CPU,这就违反了 `C6·共用一个内核`:记账不能比干活还贵。

零钱是批发:一次从池子里拿 5 ms,拿回来慢慢花,花的时候谁也不打扰。

**代价是什么?** 不那么准了。池子空的时候,别的核手里可能还攥着没花完的零钱;反过来,零钱也可能被花成负数。所以上一节 §10.1 量到的每周期用量是 49 969 μs 而不是整 50 000,§10.6 里「按权重分到 40%」的那一幕也会有些周期碰到 50 ms 的线。

**为什么一份是 5 ms?** 因为份越大越省锁(`C6·共用一个内核`),但份越大,散落在各核手里、暂时没人用的额度就越多,上限就越不准(`C2·上限要是绝对数`)。要在两者之间取一个折中,所以引入「一份」这个量,默认 5 ms,是 100 ms 周期的二十分之一。这个数可以调(实验机上 `/proc/sys/kernel/sched_cfs_bandwidth_slice_us` 的值是 5000)。更精确的推导留给读源码那一步。

| 没有它会坏在哪 | 它解决了 |
|---|---|
| 每笔账都抢全组的锁,核越多越慢 | 89% 的记账只动本核的数 |
| 记账开销随进程数、核数上涨 | 去公共池的次数只和「额度 ÷ 5 ms」有关,每周期 10 次上下 |

悬念:同样的做法,能不能搬到内存上?内存的「一笔」是什么?

## §5 t2 要内存:内存的账是怎么记的

**结论:worker 每拿到一个物理页,内核给它所在的组记 1 页。这 1 页也是先从本核的零钱里扣;零钱没了,才去改组的计数器,一次改 64 页,并且顺着树把父组、祖父组的计数器一起改掉。同时,这一页上会写下它归哪个组。实测吃 100 MiB:缺页 25 610 次,真正改计数器只有 400 次。**

### §5.1 概念:计数器、零钱、页上的户主

内存的账比 CPU 的简单,核心就是一个数:**这个组名下现在有多少页**。旁边写着上限(`memory.max`)。每个组的计数器还带一个指针,指向父组的计数器。

![内存的账:零钱、三层计数器、页上的户主,以及撞线之后的四步](pics/03-mem-charge.svg)

记账的时机也不用专门安排。进程第一次摸一块新内存时会缺页,内核要给它分一个物理页;cgroup 在「分页」后面加了一步:**给这个进程所在的组记 1 页。** 找组还是靠组籍。

便宜的办法和 CPU 一样:

- 每颗核有一份零钱,内容是「某个组已经预付了 N 页」。记 1 页时,如果本核零钱里有这个组的预付,N 减 1 就完事。
- 零钱没了,才去改组的计数器:**一次加 64 页**,1 页自用,剩下 63 页留在本核做零钱。

还有一件 CPU 没有的事:**这个物理页上要写下「我归 report 组」。** 原因在 §5.3。

### §5.2 实跑:吃 100 MiB,数一数

### §5.3 再逼问:为什么页上要写户主

**CPU 的账记完就完了,内存为什么还要在页上留记号?**

因为 CPU 时间花掉就没了,内存页要还。`C5·内存不可压缩` 的另一面是:一页从分出去到还回来,中间隔着很久,而且还回来的时候,当初要这一页的进程可能早就不在了。

- **页缓存。** worker 读一个文件,文件内容留在页缓存里。worker 退出了,这些页还在,还占着物理内存。上一节说过「页缓存不在任何进程名下」(§4 的约束、§6.1 的磁盘 IO),旧工具因此管不了它。现在它记在组名下:账不跟进程走,跟页走。
- **回收和释放。** 这一页被回收或释放时,要从某个组的计数器上减 1。减谁的?看页上写的户主。
- **回写。** worker 写文件,脏页稍后由内核线程写到盘上。这笔磁盘 IO 该记给谁?内核线程从页上查到户主是 report,IO 就记给 report。这正是 `C8·一笔开销跨多种资源` 要的:内存和 IO 对「谁是一组」给出同一个答案,而答案就写在页上。

**为什么一次改 64 页?** 道理和 5 ms 一样:因为改计数器要顺着树一层层往上改(`C7·限额要能层层转包`),树有几层就要改几个数,所以要尽量少去(`C6·共用一个内核`);但零钱是「账上已经记了、实际还没用」的页,攒得越多,账面就比实际偏高得越多(`C4·账要记在物理消耗上`)。所以引入一个批量,取 64 页(256 KiB)。4 颗核各攥 63 页,最多偏 1 MiB 上下,对 300M 的组可以忽略。更精确的推导留给读源码那一步。

| 没有它会坏在哪 | 它解决了 |
|---|---|
| 每次缺页都改全组共享的计数器,还要爬一遍树 | 98.4% 的记账只动本核零钱 |
| 页还回来时不知道该减谁的账 | 页上写着户主 |
| 页缓存、回写的 IO 没有主 | 跟着页上的户主走 |

悬念:账会记了。那 CPU 的 50 ms 花完的那一刻,这个组的进程是怎么停下来的?

## §6 t3 50 ms 用完:进程是怎么被摁住的

**结论:公共池空了以后,某颗核再来领额度就领不到。内核在这颗核上给 report 组挂一块「限流中」的牌子,组里的进程各自在下一次要回到用户态时看到牌子,自己下场,挂到等候名单上。下一个周期定时器一响,池子补满,牌子摘掉,名单上的进程放回去。4 颗核一起花,50 ms 十来毫秒就花完,剩下八十多毫秒全组都停着。**

### §6.2 逐行读时间线

- **0.00 ms**:定时器响,公共池补到 50 000 μs。

- **11.21 ms**:核 3 把最后的 864 μs 领走,池空。

### §6.3 回收一个旧问题:为什么有的 worker 拿 12%,有的只有 4%

第一节留了一个问题:一组一模一样的死循环,都在同一个半颗核的组里,为什么有一个拿到 12%,其余只有 4% ~ 6%?

答案就在上面两段输出里:**额度是按核领的,不是按进程发的。**

- 四颗核各自来公共池领零钱,先到先得,每颗核每个周期大致领到 11 ~ 15 ms,3 秒平均下来每颗核都是 12% 左右。
- 这 12% 由这颗核上的 worker 平分。核 0、核 1 上各只有 1 个 worker,独得 12.3%;核 2 上 2 个,各 6.0%;核 3 上 3 个,各 4.0%。
- 规律就是 12.5% ÷ 这颗核上的 worker 数:1 个是 12.5%,2 个是 6.25%,3 个是 4.2%。第一节看到的 12% 和 4% ~ 6% 正是这三档。

`cpu.max` 保证的是组的合计(48.6%,接近 50%),不保证组内每个进程一样多。这和上一节 §10.5「组的份额是在每颗核上各自兑现的」是同一件事的两个侧面。

### §6.4 400 个进程是怎么「同时」停下来的

上一节的悬念:400 个 worker 散在 4 颗核上,是谁、用什么办法把它们同时摁住的?

```
### 8 个 worker                                    ### 400 个 worker
1 秒内,report 组:                                 1 秒内,report 组:
  周期定时器响 10 次                                 周期定时器响 10 次
  「在某颗核上标记限流」 40 次                       「在某颗核上标记限流」 40 次
  「在某颗核上解除限流」 40 次                       「在某颗核上解除限流」 40 次
  「某个进程被请下场」   80 次,涉及 8 个不同的进程    「某个进程被请下场」   4000 次,涉及 400 个不同的进程
```

(两段输出来自同一份留档,这里并排放,原样见图。)

![终端留档:8 个和 400 个 worker 时,标记限流都是每秒 40 次;进程被请下场分别是 80 次和 4000 次](pics/03-shot-t3n.svg)

- **挂牌子的次数和进程数无关。** 8 个也好,400 个也好,都是每秒 40 次:4 颗核 × 10 个周期。内核要做的决定只有「这颗核上这个组没额度了」,一颗核一次。
- **下场是每个进程自己走的。** 80 = 8 × 10,4000 = 400 × 10:每个进程每个周期下场一次。
- 所以答案是:**没有谁去挨个摁住 400 个进程,也并不是同时。** 内核只挂 4 块牌子;每个进程在自己下一次要从内核回到用户态的那一刻看见牌子,自己退到等候名单上。

**为什么要等到「回用户态的路上」才下场?** 如果在任意位置把进程冻住,它可能正在内核里拿着一把锁,比如正在改某个文件系统的结构。它一停就是八十多毫秒,别的组的进程要用这把锁,也得跟着等。限 report 的额度,结果拖慢了 db,限流就越界了。等进程走到回用户态的那一步,它在内核里的事已经办完,手里什么锁都没有,这时候停下最干净。

据我所知,在这个位置下场是比较新的内核才有的做法(印象中是 6.18 前后改的),更早的内核是把这个组在这颗核上的整个队列直接摘下来。这句话是凭记忆写的,记入待核,讲来路时配出处。

**为什么连 fork 都要排队?** 上一节 §10.1 看到,在半颗核的组里起 400 个 worker 要等很久。fork 是主进程在内核里执行的一段代码,也要花 CPU 时间;主进程自己也在这个组里,也花这个组的额度。池子一空,它和 worker 一样下场。限额管的是「这个组的进程占用 CPU 的时间」,不区分这段时间在干什么。

### §6.5 再逼问:定时器是来查岗的吗

不是。定时器每 100 ms 响一次,做的事只有两件:**把池子补满,把牌子摘掉。** 它不查任何人用了多少。

发现「用完了」的,是来领零钱的那颗核自己。整个机制里没有巡查:账是进程跑的时候顺手记的,限是领零钱的时候顺手查的。

| 没有它会坏在哪 | 它解决了 |
|---|---|
| 要有人周期性扫描所有组、所有进程的用量,组越多越贵 | 超限在领额度的那一刻被发现,不需要扫描 |
| 要挨个通知 400 个进程停下 | 每颗核挂一块牌子,进程自己下场 |
| 在内核里冻住进程会连累别的组 | 只在回用户态的路上下场 |

留下的代价上一节说过:延迟毛刺。一个请求如果在 16 ms 这个时刻到达 report,要等 84 ms 才有人处理它。

悬念:CPU 超了可以等。内存超了等不来,那一刻又是什么样?

## §7 t4 撞上 300M:先回收,收不动才杀

**结论:某一次给计数器加 64 页会超过上限,这次记账就不成立,撞线的进程被扣在原地。它自己先动手在本组的范围内回收内存;收够了就继续跑,收不动就进入组内 OOM:给本组的每个进程打分,杀掉分最高的。被杀的是组里最大的,不一定是撞线的那个。**

   0.42 ms  回收:pid 8198(cat)自己动手在 report 组里回收,想要 512 页,收回 776 页

**读数。**

- 上限 300M = 76 800 页。账上 76 672 页时,`cat` 要再记 512 页(读文件时内核一次读进来一大块),76 672 + 512 > 76 800,撞线。
- **回收的是 `cat` 自己**(pid 8198)。没有后台线程替它干,谁撞线谁动手。回收的范围只有 report 组名下的页:内核顺着「页上写的户主」找,别的组的页它不碰。
- 每次撞线都收回了七百多页,够用,回到记账,继续读。
- 整个文件读下来撞线 146 次,回收 146 次,共收回 77 312 页 = 302 MiB,正好是 600M 的文件减去 300M 的上限。OOM 0 次。`memory.events` 里的 `max 146` 就是这 146 次撞线。上一节 §10.7.1 看到的 `max 53` 也是这个计数。

文件照样读完了,只是慢一点:`cat` 花了一部分时间替自己腾地方。

### §7.3 再逼问

**为什么不杀撞线的那个?** 撞线的只是最后一根稻草。它可能只占了很少的内存,杀了它腾不出多少,马上又会撞线。杀最大的,一次腾出最多。

**为什么不干脆让这次申请失败,返回一个错误?** 因为大多数时候没有地方可以返回错误。worker 不是在调用一个「申请内存」的函数,它只是往自己已经申请到的地址里写了一个字节,这时才缺页、才真正要物理页。一条赋值语句没有返回值。内核要么给它这一页,要么让它没法继续执行。这是 `C5·内存不可压缩` 落到实处的样子:CPU 不够可以让它等,内存不够没法让一条写内存的指令「等一等」。

**边界是谁划的?** 你的第二个灵魂问题。从上面的时间线能直接读出来:

1. 撞线撞的是 **report 组的计数器**。如果是 host01 的计数器先超,撞的就是 host01 的线(§5.2 里每次改账三层都要比一次)。
2. 回收只在**撞线的那个组**的范围里做。
3. 打分只给**撞线的那个组**里的进程打。db 组的进程、宿主机上别的进程,根本不在名单上。

所以边界 = 撞线的是哪一层的计数器。哪一层的上限是谁写的,边界就是谁划的。上一节 §10.7 里同样的进程,一次死 db-sim、一次死 report-w,区别只在于先撞线的是 host01 的计数器还是 report 的计数器。

| 没有它会坏在哪 | 它解决了 |
|---|---|
| 内存超了只能等全机见底,由全机 OOM 挑人,可能杀到别的业务 | 在组的计数器上撞线,回收和杀都限在这个组里 |
| 页缓存撑满也要杀进程 | 先回收,能扔的先扔 |
| 回收的开销摊给全机 | 谁撞线谁动手 |

## §8 把账放回树上:父组是怎么跟着动的

**结论:树上每一层都有自己的账和自己的限。内存:子组改计数器时,顺着父指针把每一层祖先都改一遍、比一遍。CPU:每一层都有自己的额度池,进程跑掉的时间每一层都扣,哪一层的池空了,那一层下面的进程全停。**

内存这边 §5.2 已经看到了:每次改账,report、host01、根三个数一起加 64。

## §9 退一步看:cgroup 是一个框架,不只管 CPU 和内存

**结论:前面跟着 worker 走过的五个时刻,只有 t0(组籍)是 cgroup 核心自己的事,t1 ~ t4 是 cpu 和 memory 两个「控制器」的事。核心把「怎么分组、怎么继承、怎么暴露成文件、建组和入组时通知谁」做了一遍;每种资源作为一个插件接进来,只需要回答三个问题:在哪里记账、限写成什么、超了怎么处置。这台内核上这样的插件有 9 个。**

### §9.1 你的视角

你读完前三节后指出的:

> cgroup 不止能管理 CPU,还能管理内存、IO。这个没有着重讲解。它可以管理各种资源,是个架构,这个特点其实可以借用到很多系统中,这是个重要的启示。

说得对,而且是前三节的一个缺口。第一节只在关键词表里用一行提了「控制器」;第二节用旧工具试过磁盘 IO 和进程数,但放进组里重演时只演了 CPU 和内存;这一节跟着 worker 走的也只有这两条线。结果是读下来容易以为 cgroup 是「限 CPU 和内存的东西」。它其实是一个放之于各种资源都成立的骨架。这一节把它补上,第一节 §4.1、第二节 §8.3 和 §10.8 也各补了一处。

### §9.2 概念:核心和控制器

![cgroup 是一个框架:核心四样东西只做一遍,每个控制器只回答三个问题](pics/03-framework.svg)

**核心**不认识任何一种具体资源,它只做四件和资源无关的事:

| 核心提供的 | 是什么 | 前面在哪见过 |
|---|---|---|
| 树 | 目录就是组;父组决定往下开哪些控制器(`cgroup.subtree_control`) | §2、§8 |
| 组籍 | 进程身上的指针;一张组籍里每个控制器一个格子;fork 继承 | §3 |
| 文件接口 | 每个控制器登记自己的一组文件,文件名前缀就是控制器名;读写和权限由核心统一处理 | §2 |
| 生命周期通知 | 建组、删组、进程入组、fork、退出时,核心挨个通知登记过的控制器 | 这一节 §9.3 |

**控制器**是负责某一种资源的那部分内核代码。因为 `C1·业务是一组进程`、`C3·被管者不可信`、`C7·限额要能层层转包` 这三条对任何资源都一样,而「在哪里记账」(`C4·账要记在物理消耗上`)和「超了怎么处置」(`C5·内存不可压缩`)每种资源都不同 → 要解决「分组这件事只做一遍,新增一种资源不用重做」→ 所以引入**控制器**这个概念:它向核心登记一张固定格式的表,核心在约定的时刻按表上的函数通知它;除此之外它只管自己那种资源的三个问题:

1. **在哪里记账**:把记账的动作埋在这种资源被消耗的那条路上。
2. **限写成什么**:暴露哪几个文件,数字是什么含义。
3. **超了怎么处置**:等、拒绝,还是回收和杀。

回头看 §0 的三件事:**组籍属于核心;账和限属于控制器。** t0 是核心的戏,t1 / t3 是 cpu 控制器的戏,t2 / t4 是 memory 控制器的戏。

- **这台内核认识 9 个控制器。** 第一行就是清单。

- **开一个控制器,核心就请它给子组建一本账。** 「建账」那四行,每个控制器被叫到的是同一类函数,名字都是 `<控制器>_css_alloc`:`pids_css_alloc`、`cpu_cgroup_css_alloc`、`blkcg_css_alloc`(io)、`mem_cgroup_css_alloc`。四个控制器互不认识,核心按同一张表挨个叫。
- **组籍是「每个控制器一个格子」。** 一开始五个格子都指向 host01:demo 自己没有任何一本账,它的进程花的资源都记在父组 host01 的账上。开了 pids,pids 那一格改指 demo,其余不动,而且**组籍换了一张**(地址从 `…cb982c00` 变成 `…cb39b800`):格子里的内容变了,就是另一张组籍。全开之后,cpu、io、memory、pids 四格指向 demo,cpuset 没开,仍指向 host01。

上一节 §12 末尾说过,v2 只留一棵树之后的折中是「同一棵树上,不同资源可以分到不同的深度」。上面第三、四条就是它在内核里的样子:一个组没开某个控制器,那种资源的格子就指向最近的、开了这个控制器的祖先。

拒绝  pid 9104 要 fork:report 组的进程数账 20,上限 20,再加 1 就超 → fork 失败(返回 -11)
pids 控制器一共被问了 20 次

和内存那条线逐项对照:

| 三个问题 | memory(§5、§7) | pids(这里) |
|---|---|---|
| 在哪里记账 | 内核分出一个物理页时 | fork 的路上,核心问一句「能生吗」(`pids_can_fork`) |
| 账长什么样 | 已用页数,带父指针 | 已有进程数,带父指针。实测 report 和 host01 两本账一起从 2 加到 4 |
| 限写成什么 | `memory.max` | `pids.max` |
| 怎么发现超限 | 加上去,看超没超 | 一样。20 + 1 > 20 |
| 超了怎么处置 | 回收,收不动就杀 | **拒绝**:这次 fork 返回错误(-11 就是 `EAGAIN`),谁也不用死 |
| 事件记在哪 | `memory.events` 的 `max` | `pids.events` 的 `max 1` |

骨架一模一样,只有最后的处置不同,而处置不同是因为资源的性质不同:fork 是一个有返回值的系统调用,可以直接说「不行」;§7.3 说过,往内存里写一个字节没有返回值,所以内存只能回收或杀。

上一节 §6.2 的两个洞也顺带补上了:`ulimit -u` 数的是「这个用户」的进程,而且对 root 不生效;`pids.max` 数的是这个组的,这次 fork 的就是 root。

### §9.5 同一副骨架,换成磁盘 IO

IO 的实跑放在上一节 §10.8(和 §6.1 的旧工具对照着看),这里只取结论:

- report 组在这块盘上限每秒写 10 MiB(`io.max` 里写 `253:0 wbps=10485760`),写 50 MiB:不设限 0.007 秒,设限后 5.0 秒。
- **带缓冲的写也限住了**(5.0 秒)。这种写是先进页缓存、稍后由内核线程写盘的,发 IO 的不是 report 的进程。它之所以还能记到 report 头上,靠的是 §5.3 说的「页上写着户主」:内核线程写这一页时,顺着页找到 report,IO 记给 report。这是 `C8·一笔开销跨多种资源` 的兑现,也是 memory 和 io 两个控制器通过同一棵树、同一个户主对上账的地方。
- 组的账在 `io.stat` 里:三次各写 50 MiB,`wbytes` 依次是 52 428 800、104 857 600、157 286 400。

| 三个问题 | io |
|---|---|
| 在哪里记账 | 读写请求交给磁盘之前 |
| 限写成什么 | `io.max`:每块盘每秒多少字节、多少次 |
| 超了怎么处置 | **等**:请求排队,到时间才放行。和 CPU 一样,带宽下一秒还会有 |

IO 这条线没有用跟踪工具抓内核里的现行,上表第一行和第三行出自内核文档对 io 控制器的说明([cgroup-v2 文档 IO 一节](https://docs.kernel.org/admin-guide/cgroup-v2.html#io))和上面的实测现象,内部细节留给以后。

### §9.6 九个控制器,三种处置

| 控制器 | 管什么 | 超了怎么处置 | 本文讲到哪 |
|---|---|---|---|
| cpu | CPU 时间(上限 `cpu.max`,比例 `cpu.weight`) | 等到下个周期 | §4、§6 细讲 |
| memory | 物理内存,含页缓存(上限 `memory.max`,保护 `memory.low`) | 组内回收,收不动就组内杀 | §5、§7 细讲 |
| io | 每块盘的读写带宽和次数(`io.max`、`io.weight`) | 请求排队等 | §9.5,上一节 §10.8 |
| pids | 进程和线程的个数(`pids.max`) | 这次 fork 失败 | §9.4 |
| cpuset | 能用哪几颗核、哪些内存节点 | 不记账,只划范围 | 不展开 |
| hugetlb | 大页的用量 | 缺页时拒绝 | 不展开 |
| rdma | RDMA 网卡上的资源 | — | 不展开 |
| dmem | 设备自带的内存区域(如显存) | — | 不展开 |
| misc | 其他只能数个数的资源 | — | 不展开 |

后五行的「管什么」取自 [cgroup-v2 文档](https://docs.kernel.org/admin-guide/cgroup-v2.html#controllers)各控制器的开头一段,没有实跑;rdma、dmem、misc 的处置方式我没有查,留空。

处置只有三种,由资源的性质决定,不由 cgroup 决定:

- **会再生的资源**(CPU 时间、IO 带宽):等。下一个周期、下一秒还会有。
- **能当场拒绝的资源**(进程数、大页):这次不给,返回错误。
- **占了不还、又没法拒绝的资源**(内存):回收,收不动就杀。

也有不太合身的地方,照实说:cpuset 根本不记账;内存没有按比例的旋钮(上一节 §10.7);v2 里管设备访问的那个控制器干脆没有文件,靠挂在组上的 BPF 程序实现(文档原话:「has no interface files and is implemented on top of cgroup BPF」)。框架规定的是骨架,不是每个插件都长得一样。

### §9.7 启示:这个形状可以带走

把 cgroup 这个名字拿掉,剩下的是一种做法:

> **把「对象怎么分组、怎么继承归属、怎么暴露接口、生命周期里什么时候通知谁」做成公共的一层,只做一遍;每一种要管的东西作为插件,只填一张固定的表。**

你在前两期已经见过两次同样的形状:

| 系统 | 公共的一层(只做一遍) | 插件 | 插件填的表 |
|---|---|---|---|
| cgroup | 树、组籍、文件接口、生命周期通知 | cpu、memory、io、pids…… | 建账、入组、fork 时的回调 + 一组文件 |
| VFS(文件 IO 那一期) | 路径查找、打开的文件、页缓存 | ext4、xfs、tmpfs…… | 一组文件操作函数 |
| 调度器(调度器那一期) | 核心调度循环、每颗核的运行队列 | 普通任务、实时任务、deadline 任务等调度类 | 入队、出队、挑下一个 |
| MySQL | server 层:连接、解析、优化、执行 | InnoDB 等存储引擎 | 存储引擎接口 |

(后三行是按我对这些系统的了解写的类比,只在「公共层 + 插件填表」这一点上成立。)

从 cgroup 这个例子里能带走三条判断:

1. **什么时候值得做成这样。** 有一件事对所有品类都一样、而且容易做错(这里是分组、继承、权限:`C1·业务是一组进程`、`C3·被管者不可信`、`C7·限额要能层层转包`);品类会不断增加(cgroup 的控制器从最初的几个长到现在 9 个);新增一个品类不应该惊动已有的。
2. **公共层要管到哪里为止。** v1 也是「核心 + 控制器」,但它把「树长什么样」也交给了控制器,每个控制器可以有自己的树,结果控制器之间对不上账(上一节 §9.2)。v2 把这个自由收了回来:树只有一棵,所有控制器共用同一套分组。**凡是插件之间需要对账的东西,必须由公共层统一规定,不能留给插件各自决定。** 这是 `C8·一笔开销跨多种资源` 给的教训,也是这个框架最不显眼、最值钱的一条。
3. **插件之间的差异要留在哪里。** 留在「记账点」和「处置」上。这两样由资源的性质决定,公共层不该替它们做主。cgroup 的核心完全不知道「超了」是什么意思。

如果哪天要在自己的系统里做多租户的资源管理,比如给数据库加资源组,可以直接套这张表来问:会话怎么归到组上、新会话怎么继承(组籍);每种资源在哪条路径上记账、记给谁(账);限写成什么、超了是排队、拒绝还是杀掉查询(限);哪些事要所有资源共用一个答案(公共层)。

## §11 最小伪代码

把上面的骨架写成六十行伪代码。不是内核源码,变量名是为了好读起的;每个函数对应前面的一个时刻。

```python
# ---------- 三件事 ----------
class 组籍:                      # §3 进程 → 账 的那张卡片(同组进程共用一张)
    cpu账: "组的CPU账"; 内存账: "组的内存账"; 进程名单: list

class 组的CPU账:                 # §4 挂在树节点上;每一层各有一本
    额度, 周期 = 50_ms, 100_ms    # ← cpu.max(组的限)
    公共池 = 0                    # 全组一个,带锁
    零钱 = [0, 0, 0, 0]           # 每颗核一份,不用锁
    限流中 = [False] * 4          # 每颗核一块牌子
    父 = None                     # C7·限额要能层层转包

class 组的内存账:                 # §5
    已用页, 上限页 = 0, 76_800     # ← memory.max(组的限)
    父 = None

# ---------- t0:fork ----------
def fork(父进程):
    子 = 复制(父进程)
    子.组籍 = 父进程.组籍          # 只抄一个指针          C1·业务是一组进程
    子.组籍.进程名单.append(子)
    return 子

# ---------- t1 / t3:CPU ----------
def 结算运行时间(进程, 核, 跑了多久):      # 时钟中断、切换进程时都会走到
    账 = 进程.组籍.cpu账                   # 一步拿到账       C6·共用一个内核
    while 账:                              # 每一层都扣       C7·限额要能层层转包
        账.零钱[核] -= 跑了多久            # 只动本核的数,不加锁
        if 账.零钱[核] <= 0:
            with 账.锁:                    # 零钱花完才来这里
                领 = min(5_ms - 账.零钱[核], 账.公共池)
                账.公共池 -= 领; 账.零钱[核] += 领
            if 账.零钱[核] <= 0:
                账.限流中[核] = True       # 挂牌子           C2·上限要是绝对数
        账 = 账.父

def 返回用户态(进程, 核):
    if 这颗核上它的某一层祖先.限流中[核]:
        挂到等候名单(进程)                 # 自己下场,手里没有锁

def 周期定时器(账):                        # 每 100 ms 响一次,只补不查
    账.公共池 = 账.额度
    for 核 in range(4):
        账.限流中[核] = False; 放回队列(等候名单[核])

# ---------- t2 / t4:内存 ----------
def 缺页(进程, 核):
    页 = 分一个物理页()
    账 = 进程.组籍.内存账
    if 本核预付[核].get(账, 0) == 0:       # 零钱没了
        记账(账, 64, 进程)                 # 一次批发 64 页    C6·共用一个内核
        本核预付[核][账] = 64
    本核预付[核][账] -= 1
    页.户主 = 账                           # 页上写户主        C4·账要记在物理消耗上、C8·一笔开销跨多种资源

def 记账(账, n, 进程):
    while True:
        撞线的 = None; 层 = 账
        while 层:                          # 顺着树每一层都加、都比   C7·限额要能层层转包
            if 层.已用页 + n > 层.上限页: 撞线的 = 层; break
            层.已用页 += n; 层 = 层.父
        if not 撞线的: return              # 没超,什么都不发生
        撤销已经加上去的那几层()
        if 在这个组的子树里回收(撞线的) > 0: continue     # 谁撞线谁动手
        受害者 = max(撞线的.子树里的所有进程, key=占的页数)   # C5·内存不可压缩
        发SIGKILL(受害者)                  # 不一定是撞线的那个
```

## §12 朴素方案对比真实方案

| 问题 | 朴素的做法 | 坏在哪 | 真实的做法 | 约束 |
|---|---|---|---|---|
| 怎么知道进程属于哪个组 | 每个组存一份 pid 名单,要用时去查 | 记账每秒几十万次,每次查名单太慢;名单和进程容易对不上 | 进程身上一个指针,指向组籍 | `C1·业务是一组进程`、`C6·共用一个内核` |
| 怎么知道组用了多少 | 定期把组里每个进程的用量加起来 | 进程退出了数就丢了;页缓存不在任何进程名下;上一节实测 400 个进程加起来还不准 | 消耗发生时直接记在组的账上 | `C4·账要记在物理消耗上` |
| 账记在哪 | 全组一个计数器,每次都改它 | 多核抢一把锁,核越多越慢 | 每颗核一份零钱,批量从共享的账上领 | `C6·共用一个内核` |
| 怎么发现超限 | 后台线程定期检查每个组 | 检查有间隔,间隔内可以超很多;组越多越贵 | 记账那一刻顺手比 | `C2·上限要是绝对数` |
| CPU 超了怎么停 | 给组里每个进程发信号让它停 | 400 个进程发 400 次;进程在内核里拿着锁时停下会连累别人 | 每颗核挂一块牌子,进程回用户态时自己下场 | `C6·共用一个内核` |
| 内存超了怎么办 | 等全机内存见底,全机挑人杀 | 杀到别的业务 | 在组的计数器上撞线,组内回收,组内杀 | `C5·内存不可压缩` |
| 父组怎么管子组 | 父组的上限除以子组个数,分给每个子组 | 子组之间不能互借,闲着也是闲着 | 每一层有自己的账,子组记一笔,每层祖先都记一笔 | `C7·限额要能层层转包` |

## §13 三个常见误解

**误解一:`cpu.max` 写半颗核,组里每个进程就各限到半颗核,或者至少大家平分。**

都不是。限的是全组合计。合计之内怎么分,看进程落在哪颗核上:§6.1 里 7 个一模一样的 worker,拿到的是 12.3% / 12.3% / 6.0% / 6.0% / 4.0% / 4.0% / 4.0%。额度是各颗核来领的,不是发给进程的。

**误解二:内核里有个监工,定期检查各个组用了多少,超了就处罚。**

没有监工。账是进程自己消耗资源时顺手记的,限是记账那一刻顺手比的。整个机制里唯一的定时器是每 100 ms 响一次的周期定时器,它只做「补满、摘牌子」,不查任何人。内存这边连定时器都没有。

**误解三:OOM 杀的是把内存撑爆的那个进程。**

杀的是撞线的那个组里占内存最多的进程。§7.2 里撞线的是 pid 8242,被杀的是 8233 和 8237,8242 活到了最后。「谁触发」只决定了 OOM 发生在哪个组、发生在什么时刻。

## §14 约束回扣

| 组件 | 对应约束 | 怎么兑现的 |
|---|---|---|
| 组籍(进程身上的指针,fork 继承) | `C1·业务是一组进程`、`C3·被管者不可信` | 同组进程共用一张;指针在内核档案上,只有写 `cgroup.procs` 和 fork 能改 |
| 账挂在组上、埋在消耗路径里 | `C4·账要记在物理消耗上` | 调度器结算时间时记 CPU;分物理页时记内存 |
| 页上写户主 | `C4·账要记在物理消耗上`、`C8·一笔开销跨多种资源` | 页缓存归组不归进程;回写的 IO 顺着页找到同一个组 |
| 每核零钱(5 ms / 64 页) | `C6·共用一个内核` | 89% 的 CPU 记账、98.4% 的内存记账不碰共享的数 |
| 限写在账旁边,记账时比较 | `C2·上限要是绝对数` | 不靠巡查;超限在记账那一刻被发现 |
| 周期定时器 + 牌子 + 自己下场 | `C2·上限要是绝对数`、`C6·共用一个内核` | 每周期补满;挂牌次数与进程数无关;只在回用户态时下场 |
| 组内回收 → 组内 OOM | `C5·内存不可压缩` | 撞线的进程自己动手;范围 = 撞线的那一层的子树 |
| 每层一本账,父指针 | `C7·限额要能层层转包` | 子组记一笔,每层祖先都记、都比;哪层撞线哪层处置 |
| 一棵树、一张组籍管所有资源 | `C8·一笔开销跨多种资源` | CPU 的账、内存的账从同一张组籍出发,指向同一个组 |
| 核心 + 控制器(框架) | `C1·业务是一组进程`、`C3·被管者不可信`、`C7·限额要能层层转包` 归核心;`C4·账要记在物理消耗上`、`C5·内存不可压缩` 归控制器 | 分组、继承、接口只做一遍;每种资源只回答记账点、限、处置三个问题(§9) |

## §16 留给下一步的悬念

1. **那些数是怎么定的?** 一份零钱 5 ms、一批 64 页、周期 100 ms。这一节只说了它们各自在哪两条约束之间折中,没有说为什么是这个值。
2. **为什么改成「回用户态时下场」?** 老内核怎么做、出过什么问题。
3. **OOM 为什么有时多杀一个?** 这一节抓到了现场,两遍结果不同。判断「已经有人在死了,先等等」的条件是什么?
4. **回收到底先扔谁的页?** 上一节 §10.7 不设保护时,先读的 db 先被收。`memory.low` 是怎么插进这个顺序的?
5. **权重在树上怎么兑现?** 上一节 §10.5 里 4 个 db-sim 没铺满 4 颗核,db 只拿到 152%。
6. **统计数字怎么汇总?** `cpu.stat` 里的 `usage_usec` 是谁、在什么时候加起来的?
7. **共享的页归谁?** 两个组的进程读同一个文件,页缓存记在谁头上?
8. **控制器向核心登记的那张表长什么样?** §9.3 只看到了建账和入组两类通知,完整的表有哪些项,核心在哪些时刻按表叫人?
